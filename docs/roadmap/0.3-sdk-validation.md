# 0.3 SDK 生产能力与价值验证方案

状态：实施中，完整验收尚未完成。日期：2026-09-22。规划基线：`2d09a2ff` / `0.3.0-preview.2`；当前进展和对应源码见[执行记录](../acceptance/progress.md)。下文门槛为计划要求，不代表已通过。

本方案细化 [0.3 路线图](0.3.0.md) 的验证与交付方式。SDK 是验收对象；模板证明可独立接入，Demo 展示真实使用，测试给出可复核证据。最终回答两个问题：指定范围内能否可靠交付产品，以及选择它相对 Electron 是否值得。

## 1. 当前起点与首批适用范围

[基础切片](0.3-foundation.md) 已记录 x86/x64 Release 的模板、Demo 默认入口、Demo React 入口启动、Bridge 和关闭验证，也有独立源码与接入验证。当前 [验收记录](../../verification/acceptance.json) 的 `scope` 为 `foundation`，`sourceDeliveryVerified` 和 `releaseReady` 均为 false。本方案不改变这些结果。

下一阶段必须正面处理已有缺口：

- [已知问题](../known-issues.md) 中的重载内存增长、关闭异常尚未闭环。
- [模板连接器](../../templates/desktop-app/web/src/native.ts) 将原生返回类型声明为字符串，但当前 Host 的普通调用实际返回 Promise，现有 async 包装会等待它；事件端口仍为空实现。需要校正类型、完善标准连接器并验证事件与请求生命周期。
- [Demo 适配器](../../demos/workbench/integration/demo_bridge_adapter.cpp) 中仍注册通用桌面方法，不能把这些注册自动计入公共 SDK。
- 尚无同机同负载 Electron 性能对照，也没有完整长期运行、目标系统与产品发布验收。

首批评估对象为 Windows 桌面工具、本地文件管理或业务工作台，使用随应用发布的受控页面及明确允许的原生服务。真实项目已锁定最低 Windows 7 SP1，包含 x86；其他系统/架构组合仍需逐项登记。现有 Windows 11 开发机的 x86 进程回归只证明该机运行，不能代替 Windows 7 SP1 x86 目标环境验收。每个拟支持的组合必须独立执行安装、功能、网络、输入及生命周期测试；对外支持表只能填写实际通过的组合。

受控页面仍可能展示来自文件、剪贴板、网络响应的恶意数据，必须覆盖输入处理和权限边界。任意远程网页、现代浏览器能力、Node.js 生态兼容及进程崩溃隔离不属于当前已证明能力。Electron 本身区分主进程、渲染进程等职责，线程分工不能视为相同隔离保证。[Electron 进程模型](https://www.electronjs.org/docs/latest/tutorial/process-model)

内核维护是早期决策门槛：列出确切内核来源、可重编译路径、漏洞评估与修复责任、适用输入范围和可接受限制。Chrome 49 编译兼容、npm audit 无告警、长稳测试通过，均不能证明浏览器内核安全。如果无法形成可信维护路径，该使用范围的生产准入应保持阻塞，并单独评估内核方案。Electron 官方也把底层框架更新及不可信内容隔离作为安全责任。[Electron 安全指南](https://www.electronjs.org/docs/latest/tutorial/security)

## 2. 各交付物怎样证明 SDK

| 交付物 | 职责 | 完成标准 |
|---|---|---|
| `sdk/` | 提供公共运行时、Bridge、桌面模块及类型 | 契约明确，正常/失败/释放路径可测；不引用模板或 Demo |
| `templates/desktop-app/` | 提供最小接入和升级起点 | 仓库外生成、独立构建运行、升级回退；用户不必复制 Demo 原生代码 |
| `demos/workbench/` | 真实使用与人工回归入口 | 通用桌面和运行时能力通过公共 SDK；扫描等业务算法留在 Demo |
| 独立 SDK 测试应用（拟新增） | 验证公共 API 在真实宿主中工作 | 从已安装 SDK 编译；不链接 Demo，也不直接访问 SDK 私有实现 |
| Electron 对照程序（最小宿主已新增） | 提供相同工作负载的比较对象 | 版本锁定，页面/数据/操作可比，保留其正常安全配置；正式对照仍待执行 |
| 本地测试与报告工具 | 运行场景、采样、判定与留证 | 未执行、失败、超时、证据失配均不能形成通过结论 |

沿用现有目录，增量结构如下；独立消费者、生命周期驱动及 benchmark 双端最小宿主已落地，自动输入、采样和配对报告仍待实现：

```text
sdk/                          公共 SDK，内部模块划分另由 ADR 确定
templates/desktop-app/        最小模板
demos/workbench/              六组场景入口，保留现有默认及 React 入口
tests/
  native/                    现有原生契约测试
  web/                       现有 Web 客户端测试
  sdk/                       现有安装与交付身份测试
  acceptance-app/            已新增：公共 SDK 的独立原生生命周期消费者
  acceptance/                已新增：生命周期驱动；混合负载及故障注入待补
benchmarks/                   已新增宿主和协议草案
  hosts/soui/                公共 SDK 最小宿主
  hosts/electron/            Electron 对照宿主
  protocol/                  采样、设备与可比性协议；自动输入待完成
demos/workbench/web/benchmarks/electron-smoothness/
                              两端共用页面和确定性数据
docs/acceptance/              执行记录；支持范围、完整矩阵及决策报告待补
out/acceptance/<suite-id>/    已新增：原始样本、日志、独立构建
verification/                只归档真实执行的报告及原始证据索引
```

公共消费者禁止 include SDK 的 `src`、链接 Demo 或复制通用实现；内部单元测试可使用专用测试接缝。诊断与故障注入能力只进入测试构建，并单独测量其开销。默认 Core 运行包不携带压测工具、Electron、测试数据或诊断符号。

## 3. Workbench 六组场景与验收映射

每组场景同时提供可操作页面和可重放的测试步骤。面板显示实际启用能力、执行结果和证据编号；不支持的能力明确显示缺口，不用模拟成功填补。

| ID / 场景 | SDK 要证明的公共能力 | 关键正常与失败验收 |
|---|---|---|
| V01 通信与长任务 | 异步调用、事件、错误、取消、背压、dispose | 原生延时任务期间页面仍响应；1/32 并发；乱序响应正确关联；取消与完成竞态；注销不再回调；超量有明确拒绝 |
| V02 数据与交互 | 帧调度、输入、后台效率 | 10,000 条同实现虚拟列表、中文表单、动画、连续 resize；任务执行中仍可输入滚动；最小化后降低消耗；GPU/CPU 路径分别核验 |
| V03 桌面工作台 | window/dialog/clipboard/screen/shell | 文件及目录选择、取消、窗口状态事件、DPI 切换、剪贴板占用、外部打开校验；仅启用 SDK 模块即可运行 |
| V04 窗口与驻留 | 进程级 Runtime、多窗口、托盘、菜单、快捷键 | 主窗加两个子窗；独立会话；关一窗其余仍工作；任务中关窗；最后退出清理；快捷键冲突；Explorer 重启恢复托盘 |
| V05 资源与故障 | 导航撤销、关闭顺序、资源所有权、诊断 | 同进程重载/销毁重建；旧会话迟到消息拒绝；缺失资源或 DLL、无权限、队列过载、受控故障能定位；恢复后可继续操作 |
| V06 接入与维护 | 安装、构建、契约迁移、包与证据身份 | 仓库外生成完整业务小样；升级保留业务文件；中断/冲突安全失败；回装旧 SDK 后重新编译并运行，再升级恢复 |

V01 的扫描或计算只作为可控业务负载；任务调度、进度事件、取消与关闭清理由公共 SDK 承担。不得为了测试通过而把新的通用 Bridge 或线程实现放入 Demo。

V05 区分可恢复服务错误和内核致命故障。当前不承诺内核崩溃后同进程恢复；对致命故障验收可定位的诊断、明确失败、应用重启及业务持久化恢复，不通过强制杀进程把正常退出标为成功。

能力矩阵逐项保存：能力 ID、公开接口/版本、启用模块、消费者场景、测试 ID、适用平台、原始证据、结果、限制、缺陷及责任人。状态区分“未实现、已实现待验收、通过、失败、阻塞、不适用”。不适用需说明范围依据，不能算作通过，也不能跳过首批范围内的必需能力。

## 4. 测试分层与本地运行方式

扩展现有测试入口和收集器，不恢复远程 CI。以下是拟实施的验证档，不能当作当前已有命令参数：

| 验证档 | 何时运行 | 证据与判定 |
|---|---|---|
| 快速契约 | 每次相关修改 | 类型/协议一致性、参数限制、错误、权限、任务状态与安装行为；模拟端口结果只算单元证据 |
| 真实宿主 | Host/Bridge/桌面模块变更 | 独立测试消费者、模板、Workbench 默认与 React 路径；真实页面、事件、取消、重载与退出 |
| 性能与体积 | 影响渲染、线程、启动、序列化或依赖时 | 固定场景前后对照，Core 与各模块的运行包增量，完整进程树资源消耗 |
| 压力与故障 | 生命周期修改及候选版本 | 100 次重载、1,000 次生命周期循环、取消/关闭竞态、故障注入；候选增加 8 小时持续运行 |
| 平台与交付 | 候选版本 | x86/x64 × Debug/Release、目标系统、DPI/多屏/IME/辅助功能、完整源码重建、安装升级回退与诊断 |

测试宿主由独立监督程序设置每步及整次超时、收集退出码和诊断。超时后为释放测试资源而终止应用，结果仍必须为失败。保留失败样本与重试理由，不能只展示最后一次成功。真实桌面和性能场景串行占用同一设备，长稳测试使用前台交互、后台任务、最小化恢复及空闲阶段组成的固定混合负载。

证据绑定 SDK 版本、Git/源码身份、SDK 包、构建 ID、完整运行载荷、设备及驱动、架构/配置、场景版本、参数与随机种子、采样区间、工具版本和原始文件散列。改变被测输入后必须补跑受影响项；旧记录只能作为历史比较。

原始日志保存于本地测试输出；PR 附摘要和可获取的归档索引。报告不记录令牌或真实用户文件内容。按已有 manifest 流程串行收集证据、暂存、刷新源码清单和打包。

## 5. 生产验收门槛

这些是拟定退出门槛，不是现有测试成绩。M0 固定设备、负载、计时与回收口径；数值变更必须说明原因，并重测比较基线。

| 维度 | 首批范围的门槛 |
|---|---|
| 功能与契约 | 必需能力在公共消费者和 Demo 中均通过；正常、非法输入、拒绝、取消、销毁均有对应证据 |
| 生命周期 | 每个公开支持的生命周期模式至少 1,000 次，0 崩溃、0 死锁、0 超时；进程启动退出与同进程 WebView 重建分开统计 |
| 重载资源 | 预热后 100 次重载，统一静置时间后 Private Bytes 增长 ≤ `max(16 MiB, 10% 基线)`；检查逐轮趋势，不能只有最后一个点 |
| 资源清理 | 会话、订阅、未完成请求、任务、线程与窗口在约定结束时释放；GDI/USER/普通句柄无持续增长；缓存预算及允许残留必须预先声明 |
| 长期稳定 | 8 小时混合负载无崩溃/卡死/无界积压；分时段资源与响应指标无持续恶化；已知内存与关闭缺陷有复现和修复回归 |
| 消息与权限 | 队列、消息大小和执行并发有上限；旧会话、越权、非法来源、路径逃逸、取消竞态被正确处理；关键结果不能静默丢失 |
| 兼容性 | 已登记的系统与设备组合通过；100/125/150/200% DPI、混合 DPI 多屏、中文 IME、键盘导航及必要辅助功能逐项留证 |
| 交付与恢复 | 干净克隆和源码包可重建；独立接入；升级与回退后实际运行；业务数据保留；候选安装、签名与诊断在目标机验收 |
| 维护与发布 | 无未关闭的崩溃、数据损坏、越权或退出失败阻塞项；内核维护与依赖再分发评审完成；支持、缺陷响应与回退责任明确 |

资源回收不能以主动压缩工作集或每轮重启进程代替。8 小时与 1,000 次是候选门槛，不能据此宣称无限期无故障；实际项目上线前仍需自身数据、页面与部署环境验收。

## 6. 相对 Electron 的价值怎样衡量

使用两种比较：第一种是相同公共 Web 页面及同等宿主操作，用于定位运行时差异；第二种是两端正常优化后的同等产品体验，用于评估实际采用价值。不能只选择对某一端有利的页面，也不能削弱 Electron 的正常安全配置换取可比性。测量和针对瓶颈优化的原则参考 [Electron 性能指南](https://www.electronjs.org/docs/latest/tutorial/performance)。

锁定 M0 时可用的 Electron 稳定版精确版本、锁文件及分发载荷。同设备、系统、电源、刷新率、数据和发布构建；两端交替测试并保留顺序。记录 Chrome 49 转译/polyfill 的成本和无法等价运行的功能，不能把不支持的工作负载记为零成本。

| 指标 | 候选目标，沿用 0.3 路线图 |
|---|---|
| 热/冷启动到可交互 p95 | 分别不慢于同负载 Electron；同时记录首帧与首次成功 Bridge |
| 60 Hz 滚动/动画 | 帧间隔 p95 ≤ 20 ms，超过 33.3 ms 的间隔 ≤ 1% |
| 输入到呈现 p95 | ≤ 50 ms，且不超过 Electron 的 `max(1.15 × p95, p95 + 5 ms)` |
| 1 KiB Bridge 往返 p95 | 单请求 ≤ 5 ms，32 并发 ≤ 20 ms；业务处理耗时另记 |
| 最小静态应用 CPU | 可见空闲 ≤ 1%，最小化 ≤ 0.5%，按整机总 CPU 百分比计 |
| 稳态内存 | 整进程树 Private Bytes 争取 ≤ Electron 的 70% |
| 相同功能运行包 | 压缩及解压大小争取 ≤ Electron 的 40%，两端均包含所需运行依赖 |
| 自身体积预算 | Core 不高于冻结的 M0 干净包；全部 P1 模块合计增量 ≤ 3 MiB 解压大小 |

热启动至少 30 次，冷启动至少 10 次并定义冷态；交互每场景 5 轮、每轮 60 秒。报告原始样本、p50/p95/p99、样本量及波动，少量冷启动数据不作精确尾延迟承诺。输入通过系统事件和呈现追踪关联；若只能测到事件处理或 rAF，则按实际测量名称报告，输入到屏幕指标标为未验证。

当前可引用的 x64 Starter 起点为 41,784,168 字节解压、15,916,679 字节 ZIP，见 [基础体积记录](0.3-foundation.md)。它包含模板页面，并非已独立测量的纯 Core 空白应用；M0 要固定新的 Core 定义和载荷清单，不能悄悄更换口径。

另以同一小型工作台记录开发成本：从文档创建项目，到接通一个长任务、窗口与对话框，再执行一次 SDK 升级。登记实际工时、SDK 修改次数、原生适配代码、兼容补丁、人工支持次数及未解决问题；首次记录作为基线，不虚构节省比例。内核更新、补丁维护和调试成本纳入采用判断。

价值报告逐项列“更好、相当、更差、不可比、未测”。性能与安全差异分别披露，不用一个综合分抵消硬性缺陷。未达到 70%/40% 等目标时保留差距，是否采用由具体项目的收益和约束决定，不能转述为全面追平 Electron。

## 7. 实施次序与可审查交付

沿用 R01–R10 工作包，不重开已完成的交付基础工作。风险实验与基线采集先行，完整对照工具未完成也不应阻止复现既有关闭缺陷。

| 阶段 | 关联工作包 | 本阶段交付 | 退出决策 |
|---|---|---|---|
| A：定义与探针 | R02，R03 先导 | 支持范围、能力/证据矩阵、测量协议 ADR、独立消费者骨架；重载/关闭复现；三 WebView 共享内核实验；内核维护评审 | 固定基线及缺陷；决定多窗口可行性和首批生产范围 |
| B：核心闭环 | R03、R04 | Runtime/Bridge ADR；真实异步与事件；取消、dispose、背压；V01/V05 的公共消费者与 Demo 场景；重载/关闭修复 | 核心失败路径和资源回收通过，发布性能采样可用 |
| C：桌面能力与体验 | R05–R08 | 从 Demo 抽取标准模块；V02/V03/V04；Core/模块增量与同机性能报告 | 必需桌面场景可复用；体积和体验结果符合冻结范围 |
| D：独立交付与收敛 | R09、R10 | V06；平台矩阵、完整依赖重建与运行、长稳报告、迁移和诊断手册；支持结论 | 通过、限范围通过或继续 preview，并列明每个阻塞原因 |

第一批可拆为三个 PR：验证场景与证据契约；公共 SDK 独立消费者及生命周期复现；共享性能场景与 Electron 宿主。随后针对暴露的缺陷独立修复。生命周期、Bridge 和模块公开变更在编码前写 ADR，按现有维护者评审流程执行。

## 8. 最终交付与准入判定

交付公共 SDK 源码及开发包、最小模板、Workbench、独立测试消费者、Electron 对照源码、本地验证入口、可复跑数据、能力与平台矩阵、性能/体积报告、迁移与故障处理手册。原始日志可按 run-id 独立归档，摘要必须可追溯。源码包、SDK 包、运行包、Demo 与符号分别交付。

每个候选分别回答：

1. **工程交付是否通过**：能独立构建、接入、升级、回退并确认产物身份。
2. **指定范围的生产验收是否通过**：全部必需场景、平台、稳定性、安全维护及发布门槛有证据，无阻塞缺陷。
3. **采用价值是否成立**：相同任务的体积、内存、响应和维护成本有可信对照，差距与限制明示。

现有 `acceptance.json` 的字段语义保持不变；新范围与证据索引先按 ADR 设计，再扩展收集器。只有真实结果满足既定规则才能生成准入结论，不能由文档或测试通过率直接设置 `releaseReady`。可对特定范围作出验收结论，未覆盖能力仍保留 preview 限制；具体产品正式上线还要完成自己的部署与数据验收。
