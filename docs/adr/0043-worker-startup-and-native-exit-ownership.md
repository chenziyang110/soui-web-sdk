# ADR0043：工作线程启动与原生退出所有权

日期：2026-10-09。状态：双架构有限源码回归已完成，批准应用；完整内核验证待完成。关联 05-03；沿用 ADR0041 的 C++ 异常展开配置。

## 问题

原工作线程构造在分配 scheduler、初始化临界区、创建事件和启动原生线程之间没有完整的失败清理。线程启动返回零时仍等待 ready；TLS 写入失败仍可发布 ready。工厂在启动后才扩充注册表，扩容异常可能让真实线程失去登记。原 threadClosed 状态先于原生 HANDLE 发出退出信号，不能用它代替线程实际结束。

## 决定

构造在交接前持有 scheduler、临界区、事件和原生线程的真实所有权。事件创建或线程启动失败，释放已取得的前置资源并报告失败；TLS 建立失败，等待实际原生线程退出并查询退出码后再回收。ready 使用 release/acquire 发布，调用方只能取得已经完成 TLS 初始化的线程。

工厂在启动前于注册表锁内预留容量，启动成功后用不再分配的操作提交登记。关闭检查和线程登记使用同一把锁。注册成功的线程在实际 join 之后退出登记；未登记的构造失败不得撤销别人的线程或伪造计数归零。

退出以 Windows 原生线程 HANDLE 的等待结果和退出码为依据。只有实际退出被确认，才发布 threadClosed、关闭句柄和释放 scheduler/对象。无法确认退出或在工作线程上删除自身时明确调用 std::terminate，避免其他线程继续访问已释放的对象。这是不可恢复失败边界，不是成功关闭或资源已释放的报告。

主线程继续使用原有窗口和 Windows timer 路径。此修改不改变任务调度优先级、公开 WebThread 接口或 Windows 7 最低目标。

## 兼容性与验证

调用方需要处理可恢复的事件、启动和 TLS 建立失败；既有完整构造后的正常生命周期继续保留。普通 Task 的销毁并不代表任务执行或 producer 完成，compositor 的 admission、计数补偿和 GC 退出仍是独立工作。

回归使用实际 WebThread/WebTimer 源码及注册表/TLS 方法，检查真实事件、线程、临界区和对象释放；覆盖分配失败、启动失败、TLS 失败、延迟退出、并发关闭、正常任务/取消以及主线程 timer。故障终止在独立子进程中观察，保留实际非零退出与监督器清理结果，不将其改写为正常通过。测试终止观察器必须在对应线程安装；MSVC UCRT 的 terminate handler 属于线程数据。

2026-10-09 的 x64、Win32 回归各完成 13 个 after 直接运行和 12 个 CTest：10 个普通直接运行正常退出，3 个预期终止直接运行取得真实退出码 86 和终止前资源记录。预期终止保留非零结果及监督器清理，未声明正常 drain；两个编译阶段主程序退出 0 后仍有受控控制台尾进程，监督器退出 124，因此整体运行记录仍为 false。实际 vendor 全文件编译、最终 DLL、正常 SDK、完整 GC、目标系统和长期资源验收仍需分别完成；有限源码回归不代替这些验收。
