# 0102 — 为 discardable 图像缓存设置显式驻留记录预算

状态：采用；双架构实际 Skia 对象和像素所有权专项已通过，完整内核及应用验收另计。

## 背景

实际资源缓存使用 discardable 存储，原策略只有 1024 条记录与独立的 64 MiB 单次分配限制。
旧实现忽略正的 totalByteLimit，无法提供显式驻留字节策略。该缺陷已用实际旧 Skia 库复现。
真实图像与字体负载的首轮资源峰值为 4,310,208 字节；观测不覆盖所有图像堆或进程内存。

## 决定

Blink 初始化显式设置 8 MiB 驻留记录预算，取上述峰值的 1.5 倍后向上取二进制 MiB 整档。
discardable 模式的正 totalByteLimit 参与 LRU 淘汰；零继续表示未配置显式字节预算。
首次启用或降低预算立即淘汰；插入前先释放足够记录，以免累加溢出。
等于或超过预算的单条记录不进入缓存。原 purge 语义在等于阈值时继续淘汰，因此稳定占用严格小于阈值。
拒收和淘汰仅释放缓存持有的记录，不撤销调用方保留的 SkBitmap 或 SkMipMap 数据引用。
1024 条记录阈值、64 MiB 单次分配限制与既有 GC 周期保持独立。

## 兼容性与备选方案

不改变缓存观测 ABI 或 SDK 类布局。观测器接受正的 discardable 字节预算，保留零为 absent，
单独比较驻留字节与条目数；单次分配上限不能用于推断总缓存上限。
malloc 模式原语义保留。禁用 discardable 或缩短 GC 周期会增加不必要的分配和呈现行为变更，未采用。
这个预算不代表合法页面大小、全部图像存储、系统工作集或生产内存门槛。

## 验证与迁移

两架构使用真实 SkResourceCache、SkBitmapCache、SkMipMapCache 和内核分配器完成 10 类测试：
超大与等阈值拒收、启用/降低/提高/禁用、LRU、条目数、shared ID、malloc、独立实例，
以及位图和缩略图外部引用在拒收/淘汰后保持有效。专项不能替代完整内核重编与实际应用负载。
两架构从字节固定的完整源码重建后，必须更新 DLL、补丁、来源和 SBOM，再执行应用及缓存负载验证。
新策略不把既有 partial、busy 或未知覆盖改为通过，完整缓存预算与发布资格仍分别判断。
