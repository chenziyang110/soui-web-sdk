# ADR-0075: TaskStore map allocation request observation

Status: proposed, source-only. Native/compiler/SDK/Owned execution has not run for this slice. releaseReady=false, full cacheBudgetGate remains not-evaluated; byte budgets, quota and calibration pins are null.

## Frozen accounting scope

Observe only allocations requested through the allocator of task_store's three private unordered_maps: tasks_, operation_to_task_ and operation_to_scope_. The delegate remains std::allocator<T>; successful allocate(n) charges n*sizeof(T), actual deallocate(p,n) refunds that same request. STL rebind retains the same store-local ledger pointer, including bucket/list/sentinel/node requests the actual implementation makes. This is requested storage, not malloc usable size, allocator reserve or PrivateBytes. Public task_snapshot/operation_result/std::string types remain unchanged. String buffers use their original allocator and are NOT charged by the map allocator.

The shared ledger is an inline private member declared before all three maps. Prepared maps explicitly use that same ledger; copy assignment retains their allocator, swaps have equal allocators, and swaps do not charge or refund. Both old and candidate map allocations remain counted while they coexist. prepared_start's existing first-member Store lock remains alive until its candidate/retired maps are destroyed. Allocation exceptions and rollback refund only actual successful allocations at deallocation; failed allocations count separately and never add live bytes. No global operator new override, observer thread, purge, quota, timer, retry or history erase is added. Disabled diagnostics delegate allocations normally without recording and retain the existing all-zero disabled getter contract.

Observe one exact total of these map allocation requests, current/high-water/successful allocation/deallocation/failed allocation/cumulative allocated-and-freed requested bytes. High-water updates at allocation time, so busy periodic getters cannot erase prepare peaks. Committed/prepared/retiring stage partition is explicitly unobserved: map swap transfers role without transferring allocation ownership, and this slice does not tag each allocation by stage. It is wrong to emit phase zeros or label the live total committed-only. Empty maps may still retain buckets/sentinels; zero entries does not imply zero requested storage. At real final TaskStore destruction, map deallocation precedes ledger destruction by member order. Destroyed owners have no callable getter; no final-public-disposal receipt is provided by this slice. Data retained after a Host close but before Bridge/Store destruction is still owned data.

Snapshot strings (five fields), tasks_ keys, both operation_to_task_ key/value strings, both operation_to_scope_ key/value strings and id_prefix_ get separately enumerated field-count/size/capacity totals under the actual Store lock. Capacity excludes the terminator and may include SSO; it is not exact requested allocation and must not be added to map requested bytes as a heap total. Prepared/retiring strings, task-service owner/job/result/subscription/handler fields and pointees, all other SDK owners, allocator reserve/fragmentation and kernel caches remain explicit gaps. Short strings with large reserved capacity remain legal; no production string policy changes here.

## Independent public observation

Add separately versioned, fixed-size task_store_storage DTO and native-only getters on TaskStore, task_service and json_bridge. Do not add fields to existing runtime_metrics/tasks, renderer168/model264 or cache216 ABIs. Enabled reads use the existing service-to-Store lock order and try_lock; busy/unavailable/disabled stay explicit, saturated/inconsistent accounting cannot be interpreted as exact finite bytes. Getter never allocates JSON, copies strings, admits work or changes counters. Existing monotonic sample helpers supply the current observation envelope, with the actual Store epoch.

The stateful private allocator can change STL request footprints even with diagnostics disabled; default functional policies remain unchanged, and resource measurements must be recalibrated for the new Source. The private allocator changes TaskStore layout; no old binary SDK compatibility is claimed. SDK and consumers must be rebuilt together through the ordinary public Source/compiler/ABI/Owned chain. The installed detail header is a private representation dependency and is shipped by the existing include-directory install rule; it adds no wire operation or authority.

Acceptance collection uses only the existing --cache-observation=1 opt-in and native owner sample path. It adds a separate TaskStore storage object per alive owner and host-closed-before-owner-destruction record, with canonical decimal U64 fields and coverage/gap masks. Ordinary output without that flag keeps its original shape. JS/PS readers, runner/policies/budgets, old Native binaries and frozen outputs are outside this slice. Collected data cannot pass full cacheBudgetGate.

## Saturation and lifetime

All diagnostic cumulative counters saturate with a sticky observation flag. Current-byte/current-allocation overflow or underflow has its own sticky loss-of-exactness flag; after loss of exactness those current fields remain UINT64_MAX and deallocation cannot make them look exact or zero again. The getter keeps data with counter_saturated=true (or unavailable for a detected mismatch), never substitutes0. Accounting requires callers to preserve the existing no-concurrent-destruction contract. Test-only allocation/final-retirement seams compile only into a regression target built from the real TaskStore source; they are absent from normal SDK code.

## Verification plan and current limit

Write one normal SDK-linked public contract target plus an explicitly instrumented target using the actual TaskStore .cpp, without copied owner implementation. Cover preparation double-copy high-water, nth-allocation bad_alloc rollback and old lookup unchanged, no task-ID consumption, retained terminal history and oldest-terminal eviction, short-size/large-capacity diagnostics, disabled getters, actual Store-lock busy schedule, sticky saturation and true deallocation before final ledger retirement. Serialization checks cover exact U64>2^53, coverage masks and explicit gaps. Existing semantics/limits/cancel/renewal/closing behavior remain unchanged.

Current verification is static/pure-data only; C++ targets are not compiled or executed while Root's Native lane is occupied. A later normal SDK build and actual public consumer/ABI/Owned checks are mandatory. No inferred byte budget or quota is frozen by this ADR.
