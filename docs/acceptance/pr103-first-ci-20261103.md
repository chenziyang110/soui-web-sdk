## 最小修复及验证边界

Windows 的失败是 Git checkout 的长总路径限制，没有日志证据表明属于权限或应用控制。修复仅在 checkout step 用三个 Git 运行时变量设置 `core.longpaths=true`；不改全局配置、操作系统设置、完整源码集合、目标 SHA 或凭据持久化规则。实际效果须由新 head 的 Windows 日志验证。

模板校验原实现只匹配 `<Package>_DIR:PATH=`。CI 命令使用无类型的 `-D<Package>_DIR=...`，但原日志没有输出实际缓存行，不能仅凭错误文案断定加载了外部包。

本机现有 CMake 3.31.6 的纯数据 `cmake -P` 复现使用只设置 FOUND 的两个假 Config，无 target、编译器、工具调用或运行产物。两个调用均 exit 0：无类型输入在 `find_package` 前后保持 `UNINITIALIZED`，显式 PATH 输入保持 PATH，两者解析到相同 Config。这证实原解析器可假拒绝合法缓存；它不冒充各云端 runner 的实际缓存观测。

修复接受 PATH 与 UNINITIALIZED，同时继续拒绝缺项、重复项、空值、其他类型及 canonical 路径偏离预期安装目录的情况；实际类型与目录写入新运行记录。八项纯 Node 元数据回归覆盖合法类型、外部来源及 Runtime 部分通过的保真性，不启动 CMake、CTest 或项目程序。

首轮的 `runtimeNoGuiTestsPassed=false` 仅因驱动原先要等全链结束才置 true，与原日志两项 Passed 不一致。新汇总从两项实际完成记录计算；后续模板失败仍保留单项通过，整个 job 的失败保持。`nativeRuntimeVerified`、`releaseReady`、`signed` 等资格不因此提升。

本次修复不改 SDK/API 或系统 WebView 后端源码、测试筛选、六个标准 runner、官方依赖固定版本、只读权限、并发或超时，不启用 artifact/cache/付费资源。最终兼容性与打包结论须以新 head 的真实 CI 结果为准。
