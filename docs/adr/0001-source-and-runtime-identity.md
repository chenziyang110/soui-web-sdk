# ADR-0001：源码身份与运行载荷证据

- 状态：proposed，随 0.3 基础改动提交维护者评审
- 日期：2026-09-22
- 范围：R01、R02 的体积测量、R08 的资源部署、R09 的证据失效

## 背景

0.2 的完整源码清单包含 90 个未被 Git 收录的路径。除缓存、临时文件和自动生成的预编译头源文件外，25 个实际源码/工程文件受到上游忽略规则影响，包括 Skia debug 源码、JSON 工程及 ActiveX 头文件。工作目录的 CRLF 散列也不能直接代表 Git checkout 的内容。运行测试只检查 EXE 和 node.dll，资源改变后仍可复用成功记录；目录复制会累积旧 Web 哈希资源。

## 决定

1. 完整源码清单升级为 `soui.full-source/v2`。Git 暂存集合及 blob 原字节是生成清单的唯一入口，忽略文件不能自动进入发布包，未暂存修改会阻止生成。每项记录 `lf` 或 `none`；验证先比较原字节，再允许文本 checkout 的 CRLF 转换。Git 中原有混合换行按原字节保留，二进制不转换。清单在无 Git 的解压目录仍可验证。发布工具先验证清单，再复制到新暂存目录、再次验证，最后压缩；不再打包可变的工作目录。
2. 恢复上述 25 个原有依赖源码/工程文件的 Git 跟踪，不修改上游实现、DLL 或 LIB。上游 SOURCE-MANIFEST 保留作为导入来源记录，不能直接拿其历史工作目录列表决定发布内容。
3. SDK 开发包继续使用 v1 安装格式，新增可选的源码换行规范字段。包内及安装后的 SDK 文件维持严格字节校验；`verify-source` 按声明规范比较源码。旧 v1 包仍按原字节校验，新内容使用新的 preview 版本。
4. 应用的 `resources/` 明确为构建工具所有；禁止存储用户数据。部署时先准备新资源目录，再替换原目录，失败保留恢复路径；不删除应用目录内的其他数据。DLL、EXE、资源以完整清单参与验收，排除明确的诊断日志/符号，未知文件使打包失败。
5. 构建记录绑定编译输入（含锁文件、工具和预编译依赖）与完整运行载荷；测试开始/结束均检查身份。旧格式、空运行集合、源码或载荷漂移、测试失败都不能授权发布。历史 acceptance 留存为历史，0.3 未完成全矩阵时明确为未验收。
6. 单应用包分别交付模板与 Demo，记录逐文件大小、分类合计、压缩和解压大小、源码/载荷身份。测量本地执行，不恢复远程 CI。包大小不代表性能对齐；启动/帧时间/输入呈现的 Electron 对照另在 R02 完成。

### preview.13 许可证原始字节补充（2026-09-26）

SDK 和运行载荷对 `third_party/licenses/` 使用严格原始字节身份，因此 Git 对整个目录设置 `-text`，不再枚举少量文件。完整源码包必须与同版 SDK 包的许可证保持一致，不能依靠源码包自身清单通过来推定二者一致。

真实解压预检发现 Element Plus 许可证在工作区为 CRLF、Git blob 为 LF，导致完整源码与同版已安装 SDK 的身份不一致；源码包本身清单正确但 `verify-source` 拒绝匹配。保留旧包与失败样本，新包使用独立文件名。修正保留既有 419 文件 SDK 包的原字节，不修改 SDK 实现或包版本；回归测试会改变验证输入指纹，须重新冻结构建记录。新增许可证也受同一规则保护。

## 备选方案

- 强制所有开发者使用相同 Git 换行设置：无法覆盖已有 checkout 和解压分发。
- 只校验 EXE 或整体目录大小：无法发现等长 JS 修改、资源替换或新增文件。
- 每次删除整个应用输出目录：可能误删产品用户数据，也不适合增量构建。
- 现在更换内核或剔除未知 DLL：缺乏依赖闭包与性能证据，本阶段保留已有运行依赖。

## 兼容、迁移与回退

不改公开 C++ ABI、Bridge 协议、线程或系统要求。新项目继续锁定 SDK；0.2 已生成项目升级会更新构建工具，需要先将用户数据迁出 `resources/`。完整源码 v1 可作历史原字节校验，但新发布要求 v2；旧构建/启动记录必须重新生成。回退使用旧 SDK 包和业务备份，不能覆盖已发布的同版本包。

## 验证

回归覆盖 CRLF/LF、二进制完整性、遗漏/额外路径、路径逃逸/链接、等长资源篡改、旧证据拒绝、资源替换和无关用户文件保留。实际执行干净源码快照校验、解压校验、独立模板构建启动、两架构适用本机测试与单包体积报告。底层全量重编译、四配置矩阵和长期性能未执行时保留未完成状态。
