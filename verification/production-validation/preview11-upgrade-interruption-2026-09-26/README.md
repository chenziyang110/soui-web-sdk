## 正常升级链

从提交 `21ca3198` 的真实模板和生成器建立仓库外 `UpgradeLedger`，以冻结的 preview.10 / preview.11 SDK 包分别执行初始、升级、回退、再升级。使用同一项目逐段调用正式安装入口及构建入口；四阶段各有两个不同 buildId，共八次构建取得原始退出码 0。每阶段 x86 完整重建 Web，x64 使用经过源码/输出身份核验的 `-SkipWeb`。

应用保留模板公共任务、窗口、剪贴板和目录入口；自有账本适配器从 `SOUI_UPGRADE_BUSINESS_DATA` 指定的文件读入中文组织、三张账单、修订号，并由原生 `app.greet` 向页面返回汇总。预期为三项、总额 20,000 分、revision 17。22 个应用及数据文件（含中文 JSON 和二进制附件）在每段安装前后、各架构构建后保持原字节。这证明编译和文件保留；尚未证明账本页面显示、公共操作或业务数据运行时读取。

每个阶段另存 SDK 锁、原始构建记录、stdout/stderr/数值退出码和日志；外部原目录保留八份独立运行载荷，每份 71 文件。`raw/verification.json` 复核全部 568 个载荷文件、PE 架构、SDK 锁、构建 ID 和输入散列。固定依赖仍来自 SDK 包，此结果不代替全源码底层重编或干净机器验证。生成器本身取自 Git 原字节；SDK 更新未改业务源码。

## 实际中断失败

在独立副本中，把正式安装器的 `renameSync` 包装为“执行原重命名后暂停”。仅在旧 `sdk/include/soui/version.h` 已移入 `.sdk-install-*/old/` 时通知宿主，再实际终止该测试子进程；没有向安装器抛出可被 catch 捕获的异常。PID、准确边界、真实 `SIGTERM` 终止观察及原始输出均保留，不能将 signal 伪写成正常退出码 0。

随后正式 `verify-project` 和重试 `install` **均退出 1**，首先报告 `sdk/CMakeLists.txt` 缺失或不匹配。旧锁字节与 22 个业务文件不变；逐项检查确认 417 个旧 SDK 文件仍可从现有文件和备份恢复。但当前 CLI 没有启动时恢复入口，不能直接继续更新。失败副本与备份原样留在外部验证目录，未自动修补它们。

根因范围：安装事务只在当前进程的 catch 中回滚；`touched` 进度仅在内存中，强制退出不会进入 catch。原有包测试注入的是可捕获 I/O 异常，不能证明进程中断恢复。下一步须补齐持久事务记录、启动时检测/恢复、明确的冲突处理，并用真实终止与再次恢复验证；修改安装器前须记录恢复契约，不能仅把本失败改成预期通过。

## 原始失败和证据边界

- 首次准备漏提取生成器依赖，创建入口退出 1；第二个独立目录补齐同一提交的 `tools/sdk` 和 `tools/internal` 后成功，旧目录保留。
- 首次复核器错误假设所有包内元数据都被构建源码清单逐项列入，因此失败。修正后要求构建输入中的 `sdk-lock.json` 精确绑定整个包，源码清单未逐项收集的 `third_party/manifests/` 仅按锁记录绑定；不将这些文件冒充原生编译器读取记录。原检查器和退出日志保留。
- 原始文件按 `raw-manifest.json` 长度与 SHA-256 归档。没有归档重复 SDK 二进制、node_modules 或八套运行二进制；构建与载荷清单可定位外部原件。
- 归档内的业务 `.gitattributes` 以 `.gitattributes.snapshot` 保存原字节，避免其规则改写同目录其他原始文件的换行。暂存区逐文件散列曾检出该影响，修正存储名称后全部匹配；修正脚本保留，恢复业务样本时须还原此文件名。
- 宿主其他 QEMU 一直运行，因此本轮没有 GUI。该账本小样沿用 preview.10 应用配置，未显式启用 preview.11 会话续期，不覆盖 V01 长会话。

`sourceDeliveryVerified=false`、`benchmarkValid=false`、`releaseReady=false`。真实四阶段应用运行、任务/目录操作、安装恢复、Debug、受限账户、签名及目标机仍待验收。
