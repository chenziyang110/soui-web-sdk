# 0101 — 每个 TaskStore 默认限制为 128 MiB 请求字节

状态：决定采用；当前默认构造的实际重编、最大负载及长期验收待执行。

## 背景与证据

此前无 policy 的构造没有字节上限。两架构在同一 Source15 安装 SDK 上，
以显式 134,217,728 字节额度完成最大合法公开 Bridge 负载：1,024 条历史、
32 个在途任务、明确拒绝第 33 个并发任务，以及 64 次历史替换。
处理 1,120 次任务后自然析构退出，x64 请求峰值 86,493,104 字节，
x86 峰值 85,738,688 字节；两者没有配额拒绝。

Source16 两架构的完整 100 正式重载加 10 预热入口均自然退出并通过。
独立读取原始事件及完整输入绑定，x64 请求峰值 1304 字节，x86 为 768 字节。
这些重载基线尚未启用默认额度，不能替代下面要求的默认入口重验。
Source15 的 x64 原生重载曾自然完成，但旧外层在后置分析超时；整入口失败
原件保留，未用原生部分成功覆盖外层失败。

## 决定

发布常量 default_task_store_request_quota{134217728}，由 Core TaskStore、
TaskService 和 json_bridge 的无 policy 构造共同采用。取最大已测请求峰值
的 3/2，再向上取二进制整档，得到 128 MiB。额度只覆盖同一 Store 的私有
分配请求，包括存活、候选、退休缓冲和失败终态预留；不代表堆保留量、任意
业务 JSON、进程总内存或第三方浏览器缓存。页面不能设置或解除 policy。

## 备选、兼容与迁移

不以微型单元夹具的峰值定额，也不把进程 PrivateBytes 当作 Store 的计账。
保留无限默认会丧失这里的字节保护；更小的整档不能覆盖实测最大合法负载。
保留构造签名和类布局，无 policy 的行为变为有界；显式 std::nullopt 仍是
未配置，零仍拒绝正分配，自定义有限额度保持原语义。原生调用者如需处理
零额度下容器初始化的正分配，必须允许构造直接抛出配额异常；未构造对象没有
可读快照。该既有行为也适用于三个层级的显式 policy 构造。需要处理
超过 Bridge 输入边界的 Core 数据，应处理 task_store_request_quota_exceeded，
或显式选择合适 policy。Bridge 准入拒绝继续使用 E_TASK_STORE_QUOTA。

## 验证

旧安装 SDK 的纯观察器已自然完成 21 项：9 个默认入口与拟议额度不匹配，
12 个显式 null/4096 符合原语义。新正常 SDK 测试覆盖三个层级、diagnostics
关闭/开启、显式 null/零/有限覆盖、owner 隔离，以及超过 128 MiB 的真实请求
拒绝后计账和任务编号回滚、后续合法任务完成。保留现有 OOM、funded-terminal、
typed 和 GUI 回归；校准的 --default 必须使用实际两参数公开 Bridge 构造。
新默认需重新完成两架构最大负载和 100 重载。真实八小时、目标系统与全缓存
预算仍独立验收，不能由本决策或有限测试推定通过。
