# 0.5.0 软件路径的 100 次重载资源协议

本协议的数值由维护者在本次正式资源采样前选择。它只判定同一进程、同一冻结源码和载荷的 Miniblink 软件路径重载资源门，不宣称 M0 全部退出、整体资源合格或 `releaseReady=true`。旧 20 ms 操作循环、1 秒资源观察和历史 mixed 文档不能获得这个新门的资格。

## 固定采样与数值规则

- `mode=reload`、10 次预热、100 次正式测量，每轮完成后持续泵消息并静置至少 5000 ms。配置写了 5000 不够，原始 `step.complete` 到紧随的 `sample` 时间差必须确实达到 5000 ms。沿用现有每步骤超时，不因失败延长门限。
- 预热第 10 次 `cycle` 样本为唯一基线。正式样本是 cycle 11–110，不能换成 process、mounted、最后一轮或 Runtime 关闭后的样本。分析器重新调用真实 `validateRecords` 检查完整步骤、原顺序、PID、参数和全部采样位置。
- 私有内存允许增量 `L=max(16 MiB, ceil(baselinePrivateBytes/10))`。末 10 次的算术中位数减基线必须 `≤L`；100 次全部样本的 Theil–Sen 斜率必须 `≤L/100` 字节/轮。100 个点产生全部 4950 个点对，以真实连续轮次距离作分母。比较使用整数有理数，避免边界浮点舍入。
- handles、threads、GDI、USER 的末 10 次算术中位数不得高于基线，全部 100 次的 Theil–Sen 斜率必须 `≤0`。每一个正式样本的 `windowClasses` 名称及计数必须与基线完全相同；任意一轮增加后再消失也失败。
- 保留全部 100 个正式原件和所有预热/关闭样本，报告每项首末、最小/最大值、尾中位数和斜率。Working Set 仅作描述，没有擅自给它添加预算，也不能通过压缩 Working Set 获得资格。协议没有额外的瞬时峰值上限；峰值和每个原件仍保留用于实际所有权分析。
- 禁止删异常点、强制 GC、重启进程、主动压缩工作集来代替回收。句柄、线程、GDI、USER 或窗口类任何残留必须定位到真实所有权账本，修改方案后重新冻结并完整重验，不能在当前结果上添加豁免。

## 身份、进程与输入范围

采用当前原生收集器已有的六项资源度量以及 `EnumWindows`、子窗口和 message-only 窗口的实际 `windowClasses` 计数；不编造新的对象计数字段。对象账本以这项窗口类稳定性、四项 OS 计数趋势及维护者的源码 owner/cap 上限表记录。SDK 私有缓存、队列容量与其他长期持有对象仍单独待核对。

本门的有限 owner/cap 表如下，不能当作整个 SDK 的对象清单：

| 观察项 | 实际 owner / 上限规则 | 尚未由此覆盖 |
| --- | --- | --- |
| 重载业务窗口 | acceptance `runner` 的 window slot 1 持有 `test_window`，该模式一个活动业务窗口；窗口中的 Host 和 Bridge 由该对象持有 | 所有 SDK 私有对象/订阅容量 |
| 进程窗口类 | 收集器只枚举当前 PID 的顶层、子窗口及 message-only 窗口；基线名称和计数为每个正式样本的严格上限及下限 | 任意系统辅助窗口的实际 owner 必须按失败原件逐项解释，不能事后豁免 |
| handles / threads / GDI / USER | 当前 PID 的真实 OS 计数；尾中位数增长上限 0、全100趋势上限 0 | 每个句柄/线程的具体长期 owner，Runtime 退出后的全局内核卸载资格 |
| Private Bytes | 当前 PID 的真实 PrivateUsage，按冻结的 L 与 L/100 判定 | 个别缓存、队列、GC、峰值预算及 8h 行为 |

Root 在 launch 之前保存 `policyBytes()` 的实际字节，散列是 `POLICY_SHA256`；在原有 `soui.acceptance-request/v1` 上增加 `resourcePolicySha256` 和 `resourceScope={kernel:'miniblink',renderer:'software',processModel:'single-process'}`。原有 runId、consumerBuildId、sourceSha256、payloadSha256 和场景参数必须一致。作用域由可信 native 构建/启动入口和冻结输入确定，不接受网页自报软件路径。

分析器绑定实际 native NDJSON、Owned NDJSON、原始 context、真实整数 PID 及十进制 **字符串** creation FILETIME。原生 `run.begin.creationFileTime` 必须为字符串并与实际 Owned 主体创建时间逐字相同；缺失、数值类型、不同创建时间或添加前导零均保持 `not-evaluated`，不能只凭 PID 继承主体身份。此字段由 acceptance Session V3 的真实 `GetProcessTimes` 收集器对所有模式输出，采用该生产者并重新构建后才能测量本门。必须 root/supervisor 都为 0、无 signal/spawn/report 错误、无 stop/fallback/forced closure，Job 在恢复主线程前分配、禁止 breakaway、自然闭合且 active=0。实际 `totalProcesses=1` 且所有 `owned-member` 都是该主体；如果 console host 或其他子进程存在，不能冒称完整单进程资源口径。重复观察同一主体允许，第二个主体不允许。实际 EXE/runner 散列、cwd、argv、report 路径必须与 context 和冻结载荷绑定。

缺失原件、采样、policy、主体身份或完整当前输入时是 `not-evaluated`。完整原件中的数值、真实静置时间或生命周期顺序不满足规则时是 `failed`。分析器不把 process exit 0 单独转换为资源通过。

## 最小使用入口

三个文件采用到正常源码位置后，从仓库根运行纯边界测试：

```powershell
node --test --test-reporter=tap tests/acceptance/resource-validation.test.cjs
```

私有候选只包含这三个新增文件；它不复制现有 runner 或历史载荷。测试和分析器使用真实同目录 `runner.cjs`，以及现有 `tools/internal/delivery-identity.cjs`。因此在候选目录直接调用测试会缺少依赖；Root 先按 copy-plan 采用，或建立仅带真实依赖的测试影子目录后运行，不以人工生命周期替代实现。此候选准备期间没有运行 Node 或 native。

Root 仍使用既有 runner/serial Owned 启动入口；本分析器不启动进程。一次正式资源运行的原生参数为：

```text
--mode=reload --cycles=100 --warmup=10 --settle-ms=5000 --timeout-ms=<既有门限> --report=<本次绝对 events.ndjson 路径>
```

`resource-validation.cjs RESULT_JSON BINDINGS_JSON OUTPUT_JSON` 从原始文件独立读取，输出文件必须不存在。bindings 是 `soui.resource-file-bindings/v1`：

- `policy`、`runner` 为真实 `{path,bytes,sha256}` 文件记录。
- `source`、`payload` 是原有 `delivery-identity.snapshot` 格式的 `{root,sha256,files,inventoryRoots}`。`sha256` 为 `identity.encoded(files)` 的散列；每项相对 path、bytes、sha256 及可选 normalization 保留原样。`inventoryRoots` 列出冻结输入目录的相对路径（整个 root 用空字符串），全部成员必须存在于 frozen files。逐项当前字节和目录成员都核对；常规源目录仍排除 out/dist/node_modules/.git/.vs，唯一运行诊断排除是既有 resources/source-navigation.log。不要用任意部分列表冒充本次全部编译/载荷输入。
- `executablePath` 必须是 payload root 内实际固定 EXE；文件读取器同时核对该 EXE 和 runner 当前字节。`request.json`、`events.ndjson` 从 RESULT_JSON 同目录读取，Owned report/context 从真实 finished 指针读取。

纯 `analyzeResource` API 的 `currentInputsMatched` 只能由上述真实文件核验或 Root 已复核的等价入口提供；单元测试的合成输入只测试算法，不是验收证据。单个冻结运行的通过始终保留 `releaseReady=false`、`m0Complete=false`。这些输入记录不意味着系统 MSVC headers/libs 的完整 provenance 已验证。

1,000 次循环是独立操作门，不能继承资源资格。新的 8 小时 session 需要另行冻结逐小时规则，旧 mixed 文档不会自动续期。Modern 完整进程树、目标 OS、全局缓存预算、GUI/输入表现、卸载与整体发布资格均另行待验。

## 显式命名缓存校准

当前公开入口支持 `tools/Test-Acceptance.ps1 -ResourceCapture -CacheObservation`。原 100reload/10warmup/5000ms/20000ms、Owner、自然 Job closure 和 complete-file-bindings 的前后/finalVerified 检查不变。只有该选项才冻结 `0.5.0-named-cache-calibration-v1` policy 和 `namedCacheObservation='named-process-cache-scalars'` request，并在实际六参数后加入 `--cache-observation=1`；无选项的原策略字节不变。

`resourceRuleObservation`/`resourceGate` 仍只描述原数学规则。新增 `namedCacheCalibration` 保留基线 cycle10 与全部正式 cycle11–110 的原完成副本、实际配置、精确 QPC age、软目标比较和狭窄 retained 清理不变量。最终 `cacheObservationGate`/`captureGate` 单独组合其有限配置与覆盖：已知违反 failed，缺少新鲜完整副本 not-evaluated，显式入口两种情况均非零；只有全部有限观察和原 OS 规则通过才返回零。零出口仍不代表整体缓存预算通过：`cacheBudgetGate=not-evaluated`、`calibratedByteBudgets=null`、releaseReady=false。实际当前校准数据与后续冻结经验预算尚待维护者执行。
