# SOUI SDK 0.5.0 大型版本规划

日期：2026-10-08。状态：执行中；当前进度见 0.5.0-execution.md；所有新指标均为验收目标，不是已取得的成绩。

## 1. 版本定位与成功标准

**0.5.0：可靠、流畅、便于 Agent 使用的 Windows 桌面框架。**

在已有 C++ SDK、Miniblink/WebView2 双后端、任务与桌面服务上，完成可独立开发、自动化、验证和部署的产品闭环。建议先发布 preview，再经 RC 验收决定是否发布 0.5.0 正式版。1.0 留给公开接口稳定、维护责任明确、生产门槛闭合之后。

本版交付三个可演示、可复现的结果：

1. **用户操作流畅**：在登记设备上完成万行列表、表单、图表、缩放和后台任务并行测试，拿出实际呈现与输入延迟报告。
2. **开发者可以独立交付**：新目录创建项目，接入 C++ 长任务，构建、诊断、离线打包、升级和回退，全程有公开入口和明确错误。
3. **Agent 可以可靠操作业务**：通过具名动作、稳定界面语义和可等待任务完成与人工相同的流程，支持取消、权限拒绝、重连与故障诊断。

“全领域”通过稳定扩展接口和按需模块实现；本版用三个参考应用证明覆盖方法，不把所有行业依赖装进核心。

## 2. 当前起点与必须继承的问题

规划基于主分支 `05e7d93b6bb36904cfabaea6147552b4d62dfb70`，开发版本为 `0.4.0-preview.3`。最近发布版本仍为 `v0.4.0-preview.1`。当前 .3 的双架构 Release、依赖回归及独立项目短启动已有记录，但完整交付、目标系统、性能和生产验收仍未通过，见[本次集成记录](../../verification/pr58-2026-10-08.json)及[验收状态](../../verification/acceptance.json)。

保留现有 Runtime 所有权、渲染器边界、帧期限唤醒、隐藏暂停、公共任务和动作契约。先补已有缺口，再按测量结果优化，避免重新实现已有基础。

| 必须处理的缺口 | 0.5 的处理要求 |
|---|---|
| 现代后端普通请求与续期/清理共享有界容量 | 为控制操作提供有界保留容量；同时验证页面传输与原生队列，满载不能饿死续期或清理 |
| 软件路径资源收敛未闭合，GPU 历史重建约每轮增加一个 USER 对象 | 明确缓存上限、对象类型和释放责任；修复根因并回归，正常退出不能替代资源合格 |
| 同文档长会话、驻留/菜单、x86 间歇超时缺少完整证据 | 保留失败记录，补复现与诊断；完成真实时钟、真实输入和目标系统回归 |
| 无 Git 源码包验证漏掉历史证据 `out/` 中的受跟踪文件 | 以包清单指定文件为准，修复导出与复验规则；保留历史原件，完成解压—重建—再次复验 |
| PE 可启动的软件内核仍是独立候选 | 纳入有独立版本、清单、架构和许可证的正式可选包，重新验收最终载荷 |
| 当前版本 Win7/PE、高刷、IME/DPI、多屏、授权门槛未闭合 | 为最终候选逐项建立证据，不继承旧版本的通过结论；代码签名按下述交付策略处理 |

依据：[已知问题](../known-issues.md)、[GPU 专项](../acceptance/gpu-lifecycle.md)、[0.4 路线图](../roadmap/0.4.0.md)。开放 Issue 有些已完成代码修复，实施前应核对剩余验收，不能把“仍开放”当作“尚未实现”。

## 3. 三档运行方案与兼容范围

统一 C++/TypeScript 业务契约，分别提供现代、兼容和 PE 资源包。公开实际能力探测；应用明确要求的能力缺失时返回可诊断错误，不悄悄降低语义。

| 档位 | 建议 0.5 必测目标 | 渲染与前端策略 | 支持边界 |
|---|---|---|---|
| Modern | Windows 10 22H2 x86/x64；Windows 11 当前受支持版本 x64，具体版本在 M0 冻结 | WebView2；现代 React/Vue/TypeScript 工具链；图形加速及故障恢复按设备验收 | 使用实际 Runtime 能力，分别验证共享 Runtime 和离线固定 Runtime |
| Compatibility | Windows 7 SP1、Windows 8、Windows 8.1，分别 x86/x64 | 兼容内核和 Chrome 49 产物；受控本地页面；软件路径优先 | 公布经验证的组件和 Web API 子集；旧内核补丁与维护责任单独登记 |
| PE Recovery | WinPE 3.1 x86、WinPE 10 x64、WinPE 11 x64 的指定镜像 | 匹配架构、无静态 OpenGL 依赖的软件内核；本地资源、自带必要合法依赖 | 面向部署与恢复；字体、输入法、UIA、网络、WMI 等由镜像组件决定 |

这些都是**待验收目标**。Win7 RTM、其他 Win10 分支/LTSC、PE 5、Server、ARM64 登记为扩展矩阵，取得镜像、工具链与证据后升级支持等级。若必测行无法完成，本版继续 preview，或经明确范围修订收窄支持声明；不能写成“完美适配 Win7 以上及所有 PE”。

每行记录 OS build/补丁、架构、镜像摘要、字体与组件、显示条件、用户权限、Runtime/内核版本、验证日期和失败项。兼容功能可先在 VM 检查；性能、显示、输入和驱动结论由对应实机验证。

WebView2 109 是 Win7/8/8.1 的最后支持版本；新版前端能力不能靠冻结 109 无限延续，见[微软终止支持公告](https://blogs.windows.com/msedgedev/2022/12/09/microsoft-edge-and-webview2-ending-support-for-windows-7-and-windows-8-8-1/)。现代目标的官方范围依[微软系统支持表](https://learn.microsoft.com/en-us/deployedge/microsoft-edge-supported-operating-systems)在冻结时复核。

WebView2 团队表示 WinPE 没有官方支持，见[官方反馈答复](https://github.com/MicrosoftEdge/WebView2Feedback/discussions/4293)。PE 主程序应以原生 EXE/CMD 启动，不要求 Node、MSI、PowerShell、.NET、在线 CDN 或 WebView2；x64 PE 不假定能运行 x86 应用。镜像组件与使用范围依据[WinPE 官方说明](https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/winpe-intro?view=windows-11)登记。

## 4. 六条工作线

### W1：呈现性能与资源可靠性（发布必做）

- 分别采集输入、主线程排队、布局/绘制、Bridge、合成和实际呈现时间，定位瓶颈后优化。
- 优化连续缩放、合并刷新、帧预算、可见性调度、虚拟列表和后台任务对界面的影响；避免在 UI 线程执行长任务。
- 建立每窗口、会话、任务、线程、句柄、缓存和 GPU 对象的所有权与关闭顺序，关闭已复现的资源与退出缺陷。
- 验证图形初始化失败、设备异常、休眠/唤醒、最小化恢复、混合 DPI 跨屏切换。可以恢复时重建；需要重启时保留诊断和可恢复业务状态。
- 修复长会话控制容量及旧会话隔离；导航、重建或撤销后不接受旧请求。降级重建文档时重新授权和 bootstrap。
- 兼容内核 GPU 继续按设备实验性放行；不得将其已知缺陷带入默认支持路径。不能承诺内核致命崩溃后的同进程恢复。

### W2：Windows/PE 与现代前端（发布必做）

- 实现完整的三档构建、资源选择、启动检查、能力报告和错误说明；锁定每档 CRT/UCRT 与导入依赖。
- 补中文 IME、键盘导航、窗口工作区、100/125/150/200% DPI、多屏、托盘/菜单/快捷键、三窗口和 Explorer 重启回归。PE 缺失桌面组件的能力明确标注不可用。
- 现代模板认证 React/Vue 当前稳定版本、Vite 8 系列和 TypeScript 升级候选；精确版本在 M0 冻结，RC 前不追逐主版本。
- 为常用表格、图表、表单、编辑器建立参考组件清单与真实宿主测试；支持 ES Modules、动态导入、Worker 和现代 CSS 的程度以能力表为准。
- 将类型检查与兼容产物生成分开。TypeScript 6 弃用 ES5 target 并移除部分旧模块输出，不能直接抬高旧管线编译器后宣称兼容；采用独立转换管线或短期保留经验证的 emitter，见[官方发布说明](https://devblogs.microsoft.com/typescript/announcing-typescript-6-0/)。
- 构建机优先评估 Node 24 LTS，并验证声明的最低版本；Node 只用于开发/构建。现有 Node 20.19 接口若退役，提供迁移期和文档，不能以 Win7/PE 目标系统推导必须安装旧 Node。

### W3：Agent GUI 与统一契约（发布必做，范围受控）

- 一份受限 schema 生成 C++/TypeScript 类型、参数校验、API 文档与 Agent 工具定义；原生端始终负责最终校验和授权。
- 长操作复用公共任务服务，统一进度、取消、超时、失败、重试和幂等约定；避免新增另一套任务生命周期。
- 超时不等于取消或回滚；取消须由业务确认终态。结果未知时按 operationId 查询，普通动作不自动重放。同一幂等键同输入关联原操作，不同输入拒绝；需要真实手势的请求不得自动重试。冻结结果保留期限及跨重载/进程恢复边界，区分“重新发现状态”与“重新执行”。
- GUI Kit 提供稳定 ID、角色、状态、动作、快照和条件等待。React/Vue 绑定按需安装，不成为 C++ Core 的硬依赖。
- 首批 UIA 覆盖按钮、输入、选择/列表和任务状态；验证键盘与屏幕阅读器基本流程。敏感字段脱敏，动态节点移除后不可操作。PE 无 UIA 组件时明确降级为 SDK 语义接口。
- 本地 Agent 连接默认关闭，由应用显式启用。原生验证调用主体，授权绑定应用、窗口与会话；冻结撤销与重连规则，发现、快照、执行均按主体过滤。网页不能自行授权，普通 UIA 桌面访问不等于独立 Agent 身份，也不能产生特权动作需要的真实手势。
- 验证伪造主体、跨窗口/会话调用、撤销后调用、未授权发现、敏感状态泄露的拒绝路径。MCP 适配参考列为 P1，在本地主体与公共动作接口稳定后按容量追加；远程多人服务留待后续版本。
- 独立消费者验证“发现 → 执行 → 等待 → 完成/取消”；同时覆盖拒绝、节点消失、重载、会话撤销和旧请求重放。

### W4：标准 SDK 开发体验（发布必做）

- 在现有工具上统一 create、doctor、dev、build、test、package、upgrade 的入口和结果格式；保留现有脚本兼容入口。
- 提供最小 C++ 接入、现代应用、兼容/PE 应用三种路径，保持 `find_package` / `Soui::Sdk` 接入；业务代码不依赖 Demo 内部实现。
- 参考 UI 提供可选主题变量、明暗模式、焦点/错误/禁用状态与本地化资源约定；复用经过认证的组件，不另造一套完整行业组件库。
- 错误包含阶段、稳定错误码、缺失条件和可执行修复建议；交互输出给人阅读，结构化输出给 Agent 使用。
- 开发环境支持快捷预览与资源更新；打包过程固定锁文件、能力档位、原生载荷和 SDK 身份。
- 在全新目录及源码包中完成独立接入、搬移构建、升级/回退和业务数据保留；SDK 缺少依赖时可提前诊断。

### W5：小体积、离线交付与维护（发布必做）

- 按核心、渲染后端、桌面服务、Agent 与领域扩展拆分可选交付；模板和 Demo 不随运行核心强制分发。
- 分别公布应用 ZIP、首次完整安装、离线 Runtime、安装占用、模块增量和完整进程树内存，明确缓存或共享 Runtime 的成本。
- 现代档提供共享 Evergreen Runtime 的小应用包与固定 Runtime 的离线包。后者由应用负责更新；不能把完整内核成本从体积对比中扣掉，见[官方分发说明](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution)。
- 完成无 Git 源码包完整重建、安装被中断后的恢复、升级失败回退、离线缓存校验、SBOM/随包许可和当前二进制对应的依赖证明。
- 建立内核/依赖维护周期与漏洞响应责任；固定 Runtime 有明确更新途径。按用户 2026-10-09 的指示，本版按未签名交付准备并如实标注，不等待签名证书。后续取得签名材料时再验证签名包和目标系统信任链。
- 更新恢复先覆盖 SDK 与参考应用的明确部署方式；差分更新、全行业应用商店或通用更新服务不进入首批范围。

### W6：领域扩展与专业参考应用（基础必做，行业模块后续扩展）

建立模块能力、版本、权限、线程、取消、资源归属和数据传输契约。大数据避免通过普通 JSON 消息反复复制；先测量再决定批量或二进制通道。高权限/不稳定设备模块可独立进程隔离。

| 参考应用 | 证明的能力 | 必须完成的流程 |
|---|---|---|
| 业务工作台 | 表格/图表/中文表单/多窗口/后台任务 | 万行列表操作期间启动、取消和完成 C++ 任务；重载后正确恢复或解释状态 |
| 部署与恢复工具 | PE 离线启动/文件操作边界/原生诊断 | 在指定 PE 镜像启动，检查依赖、执行只读扫描并将日志保存到指定持久盘 |
| Agent 操作台 | 可发现业务动作/任务/GUI 语义/UIA | 人工与 Agent 完成同一组业务验收；拒绝与取消结果一致，过程可回放诊断 |

首批模块复用只读文件服务与可取消任务。数据库、音视频、工业设备、AI 模型服务、商业组件按需求选装；不承诺这些领域的全部功能或行业认证。

参考应用优先共用业务工作台和 PE 模板，Agent 操作台复用工作台的业务与组件，避免并行维护三个完整产品。新增独立行业演示按余量追加。

## 5. 可量化验收

### 5.1 流畅度

以下为提议门槛，M0 在设备和负载冻结时确认。不得在看到失败结果后悄悄放宽。对连续滚动/动画等实际需要连续刷新的场景统计；静态页面空闲另计 CPU，不将空闲间隔算丢帧。

| 已登记实机档位 | 实际呈现间隔 p95 | 长帧比例 | 输入至实际呈现 p95 |
|---|---:|---:|---:|
| 60 Hz | ≤20 ms | >33.33 ms 的间隔 ≤1% | ≤50 ms |
| 120 Hz | ≤10 ms | >16.67 ms 的间隔 ≤1% | ≤25 ms |
| 144 Hz | ≤8.33 ms | >13.89 ms 的间隔 ≤1% | ≤21 ms |

60 Hz 沿用既有路线图；高刷数字是按帧周期提出的新目标。已知现有测试显示条件为 75 Hz，不能证明 120/144 Hz；必须取得相应设备。Modern 主参考机应覆盖 60 Hz 与至少一种高刷；只有完成的高刷行可以对外宣称。Compatibility 的主要交互参考机按 60 Hz 验收，低配置/PE 另立负载和门槛，在 M0 冻结后独立判定。

每交互场景至少 5 轮、每轮至少 60 秒，S05 动效场景每轮至少 120 秒；冷启动至少 10 次、热启动至少 30 次，冷态定义单独冻结。保存原始样本、p50/p95/p99、样本量、波动与失败，少量冷启动样本不作精确尾延迟承诺。采集工具须验证对应 OS/渲染路径；rAF 只能证明回调，缺呈现/输入关联证据时相应指标保持未验证。沿用[基准采样协议](../../benchmarks/protocol/README.md)，真实中文 IME composition 不能用 Unicode 按键注入替代。

Electron 对照分别测试“同等公共页面”与“双方正常优化后的同等产品”，固定版本、安全设置、设备和数据，交替完成至少 5 组。启动、完整进程树内存、CPU、体积和输入延迟均入报告；70% 内存、40% 完整包体积沿用旧路线图作为探索目标，不作为已经实现或所有后端必能达到的承诺。依据：[SDK 验收与对照规则](../roadmap/0.3-sdk-validation.md)。

### 5.2 稳定性、体积与交付

| 维度 | 候选版退出标准 |
|---|---|
| 生命周期 | 每个公开支持模式至少 1,000 次，零崩溃、死锁、超时；进程启停和同进程重建分别统计 |
| 重载资源 | 预热后 100 次重载，统一静置后 Private Bytes 增长 ≤ max(16 MiB, 10% 基线)，逐轮趋势与对象账本同时合格 |
| 长会话 | 8 小时真实时钟混合负载，任务/订阅跨多次续期正确保留；包含满载、取消、前后台切换和权限撤销 |
| 资源与积压 | 采完整自有进程树；分小时中位数/p95 无持续恶化，无未解释的对象增长；队列/缓存有冻结上限，结束时按契约回收 |
| 异常恢复 | 故障注入覆盖加载失败、图形异常、进程退出、磁盘不足/只读、更新中断；操作不会悄悄重复，业务数据可恢复 |
| 三档兼容 | 第 3 节必测行完成对应业务流程；按能力清单检查输入、显示与可选组件，不用启动截图代替完整验收 |
| 体积 | 在 M0 固定当前 .3 的同功能载荷。核心与现有同功能模板目标不增大；新增模块逐项给增量预算，超预算须说明取舍，不能藏入共享缓存 |
| 接入成本 | 至少 2 次按公开文档从干净环境独立接入；记录时间、手工修补与求助点。工具链就绪后创建至首个窗口目标 ≤10 分钟 |
| 交付 | x86/x64 × Debug/Release 适用构建、独立消费者、无 Git 源码重建、离线启动、升级/回退、清单与许可证均通过 |

长期测试不能靠周期重启、压缩工作集或重试后只留下成功结果通过。监督程序只管理身份绑定的自有进程，先解决失败后清理问题再跑正式性能测试。

M0 必须冻结预热结束条件、静置时间、采样频率、趋势判定算法和增长/缓存预算；分别定义兼容软件、实验 GPU、现代完整进程树的统计口径，未冻结不得退出 M0。历史静置 20 ms 的千轮记录与静置 1 秒的重载记录不能套用同一资源预算。新增“无持续恶化”结论必须按冻结规则计算，不能凭曲线观感判定。

M0 同时列出 OS × 架构 × 后端/Runtime × 渲染模式 × 生命周期的必测组合，逐行指定千轮与 8 小时次数、设备和串行占用时间。可代表覆盖的项目必须说明依据；启动、ABI、输入与系统行为不能随意跨系统继承。排期包含最终载荷变更后的受影响项重跑，矩阵及时间预算未冻结不得进入正式长测。

## 6. 里程碑、依赖与资源

按约 4 名全职人员估算：2 名 C++/渲染、1 名前端/Agent、1 名兼容/交付验证。设备和镜像及时到位、无新增内核级阻塞时，经 M0 核准的首批范围建议预算 **12–16 周**；这是资源假设，不是发布日期承诺。M0 必须给每个交付切片列负责人、人周、依赖和验证耗时；UIA、主体/传输由原生负责人承担，不能全部算在前端/Agent 一人身上。单人执行不能直接套用并行工期。超出容量时先后移 MCP、额外行业模块和独立演示；必做范围仍超量则延长周期，不能压缩权限与可靠性验收。

| 阶段 | 参考周次 | 主要产出 | 退出条件 |

| M0：冻结范围与基线 | 1–2 | 系统/设备/组件与长测矩阵、性能采集、体积基线、复现列表、接口 ADR、切片负责人/人周 | 关键缺陷可复现或有充分诊断；指标、必测范围和串行验证预算可执行 |

关键依赖：先准备实机和呈现采集再宣称高刷；先修控制容量再跑长时续期；先固定 PE 内核再做系统验收；先确定动作/任务 schema 再生成绑定；先冻结最终载荷再出发布证据。各阶段可交叉开发，但这些顺序不可跳过。

需要的基础设施：可调 60/120/144 Hz 的物理显示设备、至少一台低配置兼容机、Intel/AMD/NVIDIA 中明确登记的测试组合、合法取得的系统/PE 镜像、隔离长测环境与离线测试条件；签名服务可选。若缺设备，对应结论保持未验证，并反映到版本范围和日期。

当前项目沿用本地可复现验证，不在本规划中擅自引入远程 CI。真实桌面/性能测试在同一设备上串行执行；代码与无窗口契约测试可以并行。

## 8. 发布规则与范围控制

- preview 可按里程碑发布，但能力、失败和未验证项随包公开；RC 不新增主版本依赖与核心功能。
- 同一个 SDK 版本只对应一份内容；变更影响运行输入后刷新身份并补测，不覆盖已冻结包或历史证据。
- 默认支持路径存在崩溃、死锁、越权、数据损坏、退出失败、无界资源增长、关键续期失败时不发布正式版。
- 完整源码交付与产品就绪分别判定；构建和短启动不能置 `releaseReady=true`。
- 1.0、macOS/Linux、浏览器内核重写、所有新 Web API 向旧系统回移、稳定跨编译器插件 ABI、远程多租户 Agent、全部行业模块均不进入本版承诺。
- 风险处理有明确顺序：先保可靠默认路径和独立交付，再扩设备加速与行业功能；任何范围调整都同步支持表、验收表和发布说明。

本文件保存已接受的版本范围。第一批实施任务为 05-01～05-04；其结果决定后续并行工作的可靠起点。
