# ADR-0016：就绪任务的优先级等待上限

- 状态：proposed，内核候选需两架构重编、运行回归和维护者评审。
- 日期：2026-09-26。
- 关联：Issue #35；当前 preview.15 候选已导入两份重编内核，尚未批准生产发布。

## 背景

冻结 preview.11 消费者的连续 CSS 动画使页面尾部脚本在 60 秒内不能完成加载。关闭同一动画后同一原生程序完成短测。匹配 GUID/age 的 x86 PDB 队列快照显示：主线程的 `HTMLParserScheduler::scheduleForResume` 已到期超过 10 秒、优先级 100；队列中仍有优先级 200 的页面提交任务。当前选择逻辑只按优先级和同级到期时间比较，没有长期等待补偿。

## 决定

把现有就绪任务选择提取为内核直接调用的内部策略，并在同一策略上建立原生回归。正常短暂突发仍按优先级选择，同级仍选最早到期者。就绪任务等待达到 50 ms 后进入最早到期优先范围，排在未达到该期限的任务之前；同时达到期限时选最早到期者，相同到期时仍用优先级。

50 ms 沿用现有单次调度的时间量级，用来限制严格优先级生效的等待窗口；它不是单个任务执行时间或端到端响应上界。任务自身过长、前面存在多个更早任务、线程未获调度都可能超过这个时间。未来任务不提前执行；退出清理保持原选择行为。唤醒机制、任务生命周期、取消、锁、线程和单次调度预算保持原有契约。

## 备选方案

- 移除页面动画或把脚本挪到前面：绕开复现，不能满足 V02 动画与加载并行要求。
- 永久提高 loading 优先级：会把饥饿风险转给其他任务，不采用。
- 只按任务数量轮换：一次高优先级任务耗尽时间预算时，下一次调度重置计数仍可能长期饥饿。
- 完全取消优先级：会失去正常突发时的输入/默认任务优先关系，不采用。

## 兼容与验证

没有公共 C++/TypeScript API 变化；低优先级任务在持续压力下获得执行机会，可能改变过去没有保证的跨优先级执行顺序。资源所有权和同任务取消规则不变。

先记录旧策略在持续高优先级提交场景的真实失败，再验证优先级、同级时序、未来任务、退出清理、长等待和持续补充场景。两架构重编实际内核，保持原动画、页面和时限复测，随后完成模板/Workbench/公共消费者、Win7、生命周期、资源及 V02 并行交互。原始失败不覆盖，调试器采样不用于性能数字。

实际 DLL 内容改变时增加完整 SDK 候选版本、补丁来源与清单，不能把新二进制继续作为既有 preview.13 的同一包。正式发布前仍需全部适用生产门槛；局部回归不批准生产。

## 当前执行结果

[x86 完整底层重编](../../verification/production-validation/scheduler-fairness-x86-rebuild-2026-09-26/README.md)与 [x64 重编](../../verification/production-validation/scheduler-fairness-x64-rebuild-2026-09-27/README.md)均退出 0；两个冻结消费者只替换新内核、保持原动画和期限，真实短测完成公共任务及关闭、退出 0。策略实际调用点已通过双架构内核编译和这个复现验证。新内核已导入独立新版本候选，完整当前 SDK 应用、Win7、平台/资源回归及维护者评审仍待完成，决定继续为 proposed。
