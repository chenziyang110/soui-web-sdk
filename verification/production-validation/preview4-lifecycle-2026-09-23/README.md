100 次重载从第 3 次预热末点比较到第 103 次末点；门槛是 `max(16 MiB, 10% 基线)`。它只是一条 Private Bytes 数值线，还要检查分段趋势、线程、句柄、USER/GDI、任务与订阅释放。两架构每 10 轮的中位数均有升降，未据两个端点推断稳定。1,000 次使用 20 ms 静置，检验生命周期操作，不代替每轮 1 秒的资源预算。高频运行中内存与普通句柄出现较高峰值和回收；x64 重建在约第 500 轮后出现系统输入辅助窗口类，USER 总数由 9 升至约 14，所有权及关闭后的残留仍需解释。不能只看最后一点，也不能把正常退出解释为资源门槛通过。所有监督结果仍为 `resourceGate: not-evaluated`、`releaseReady: false`。

这些运行在已验证源码/载荷身份的本机软件呈现路径执行。x86 千次重建与 x64 三窗口使用隔离副本；[冻结清单](freeze.json)记录相同的源码指纹和双架构 SDK build-id，[冻结步骤脚本](freeze-procedure.cjs)保留复制及复核方法，公共消费者 build-id 和运行载荷散列见对应 `build.json`。脚本从 SDK 根目录的 `out/` 执行，隔离副本不是完整第三方源码包。x86 三窗口与双架构 Bridge 千次、8 小时混合业务、GPU、目标系统及安全/授权仍需分别验收。运行期间失败和未执行项保持原始状态，不以旧 preview.3 候选替代本固定包。
