## 单应用体积

使用相同 ZIP 参数 `-mx=5 -mmt=2`，每包只包含一个应用，保留原内核及运行库；排除诊断日志和符号。

| 应用 | 架构 | 未压缩字节 | ZIP 字节 | 运行文件数 |
|---|---|---:|---:|---:|
| 最小模板 | x64 | 41,784,168 | 15,916,679 | 66 |
| 最小模板 | x86 | 28,355,640 | 11,913,638 | 66 |
| Workbench | x64 | 52,691,003 | 22,256,336 | 470 |
| Workbench | x86 | 39,209,739 | 18,233,863 | 470 |

相比规划时有历史残留的 x64 目录快照，模板减少约 0.92 MiB，Workbench 减少约 9.88 MiB。这是废弃 Web 资源清理结果，旧快照不是规范发布基线，不能据此声称内核变小或 Electron 性能达标。后续以本次逐文件清单作为可复核的体积起点。

## 验证中发现的问题

- 历史 VC6 头文件同时含 CRLF 与双 CR 换行，重复规范化会误报篡改。已改为 Git index blob 原字节和先原样比较的验证，补充导出→重新初始化 Git→重建清单的一致性回归。
- 一次 x86 资源替换返回 Windows `EPERM`；脚本恢复原资源并使构建失败，重新构建与运行通过。未确定外部文件占用来源，保留为实机部署观察项，不通过忽略错误处理。
- 汇总验收记录后旧源码清单被正确拒绝。发布必须先完成证据收集，再暂存修改、刷新清单并打包；不能与写入验收文件的步骤并行。
