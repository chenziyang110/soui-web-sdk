# M0 long acceptance policy

This is a newly frozen 0.5 M0 policy selected by the maintainer before actual execution. This Source packet has no actual results and does not certify release, ABI, licensing or target OS support.

Use the existing public entry after composing and genuinely reviewing the selected Source, then creating fresh current SDK/stock/consumer builds:

- Test-Acceptance.ps1 -LongRunCapture -Scenario all: four independent processes, each public mode 1000 same-process cycles; warmup0, settle500ms, step timeout20000ms.
- Test-Acceptance.ps1 -LongRunCapture -Scenario mixed: real eight-hour mixed lifecycle workload, idle10000ms.
- Test-Acceptance.ps1 -LongRunCapture -Scenario session: independent real eight-hour same-document task/subscription/renewal workload, idle60000ms.
- Existing NativeToolchain / Architecture / six tool paths / DevkitRoot parameters keep their original explicit SDK and stock ownership rules. LongRunCapture requires ordinary fixture and actual execution; it is distinct from ResourceCapture and PrepareOnly. Overriding a frozen timing value is rejected.

The old ResourceCapture entry still uses the separate 100reload protocol. The new mode cannot infer long success from that record. Process restart coverage is separate from the 1000 same-process operations.

Eight complete hours are measured from mixed's first cold cycle.begin or session's authenticated initial anchor0 sample. Samples belong to one phase: mixed cycle or session anchor. At least30 samples/hour; every adjacent and edge gap <=180000ms. Quantiles use nearest rank. Hour0 is the first full hour without removing cold points.

| Quantity | Hourly p50 and p95 rule |
|---|---|
| PrivateBytes | p50 growth <=max32MiB/ceil20%; p95 <=max64MiB/ceil25%, both relative to hour0 |
| Handles/threads/GDI/USER | no growth above hour0 p50/p95 |
| All preceding trends | exact-rational 28-pair Theil–Sen <=0 for each quantile series |
| Window classes | exact same-phase names/counts at every point |
| Action durations | p50 growth <=max25ms/ceil25%; p95 <=max100ms/ceil25%; both TS<=0, separate action/window/cycle position |
| WorkingSet | descriptive, not a substituted PrivateBytes budget |

Deliberate idle, startup/anchor mount, shutdown and final anchor close are boundary work. All logs, final cycles, incomplete tail hours and shutdown snapshots are retained. They cannot be removed as anomalies, mixed into the eight-hour trend or relabeled as RTT/presentation samples. Original step deadlines, supervision budgets, native renewal/progress and natural whole-job closure remain mandatory.

The result retains operation-result.json, long-run-policy.json, file-bindings.json, original events/Owned/context/stdout/stderr, long-run-analysis.json and final result.json. The latter separates operations, duration, cadence, PID/tree scope, OS trends, actions, bound model, actual owner capacities, contractual drain and cache budget. Known failures stay failed; exact missing evidence stays not-evaluated. Required subgates determine overall longRunGate. releaseReady is always false.

Existing PID resources equal the full tree only when actual Owned evidence proves one original member and natural Job0 with no cleanup. Child processes need real per-member samples. Published owner limits are evaluated from actual owner DTOs and unchanged Source capacity tables, not inferred configuration. Shared Engine is counted once. Busy/disabled/saturated/clock-invalid observations do not pass, and independent owner locks are not an atomic ledger.

Task cancelled terminal history and worker slots may remain; nonterminal task states and actual inflight/queues/subscriptions must drain. Retired host FIFO/adapter may be not_started after unmount, optional GUI absence is separately not_started, and borrowed revoked permission module slots are not forced to zero. Current aggregate cache coverage is incomplete: enumerated owned strings do not measure allocator/container/external borrows or third-party Blink/V8/Skia caches. That precise cache gap prevents a full eight-hour P0 claim until new actual evidence closes it.

Do not reuse historical DLLs, prepared tools, build observations or requests after Source changes. A modern build host does not establish Win7/PE target or OS-matrix compatibility; those still need independent actual matrix evidence.

The maintainer separately froze at least30 real completed durations per recurring action/window/position group per complete hour. Insufficient counts or cadence coverage are not-evaluated, with original points retained; no response percentile borrows the resource sample count. The fixed classifier checks the required-gate roster and recomputes every aggregate and mode-specific scope before it can expose passed.

The current eight-hour policy revision is `0.5.0-m0-named-cache-configuration-v2`. Both duration modes retain the mandatory `--cache-observation=1`. Independent required gates `namedCacheConfiguration` and `namedCacheCoverage` evaluate only the named completed copies: configuration success needs eligible fresh complete points; each hour needs at least30 distinct completion QPCs observed in its cycle/anchor phase, with edge/adjacent gaps <=180000ms and completed-copy age <=180000ms. Missing/partial/unsupported/stale/pending/retired points remain diagnostics and cannot contribute coverage. Known DTO contradictions or narrow retained-resource violations fail even if other coverage or full byte budgets are missing. These gates retain the existing failed > not-evaluated > passed aggregate ordering.

Soft Blink/glyph target excess is report-only; resource aggregate bytes are never compared to a single-allocation limit. Discardable resource total0 has no byte bound. Overall `cacheBudget` remains not-evaluated, so even matched named configuration and cadence cannot turn the whole eight-hour resource/long gate green. No empirical byte budget has been frozen: `calibratedByteBudgets=null`. Use the separate original100reload resource protocol with explicit `-CacheObservation` to obtain current calibration points first; it does not replace either eight-hour workload or the missing broad cache/allocator scope.

Revision `0.5.0-m0-task-request-quota-v3` additionally evaluates the emitted TaskStore private allocation-request quota for every live and retired owner in mixed/session. The configured maximum remains 134217728 bytes, matching ADR 0101. The required `taskStoreQuota` gate checks peaks, immutable owner identity, caller clocks, cumulative counters, lifecycle/cycle coverage and exact binding to the raw run. Missing or busy readings remain not-evaluated, known violations fail, and parsed analysis is recomputed before capture classification. This is neither a whole-cache budget nor proof of final C++ owner disposal. Original duration, sampling, resource/action trends, other gates and raw historical v2 records remain unchanged. No actual eight-hour run is claimed by parser tests.
