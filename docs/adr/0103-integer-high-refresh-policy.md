# 0103 — 按整数显示频率选择帧节拍

状态：采用决策；计时器和真实 Demo 控制双架构专项通过，完整候选与物理呈现验证另计。

原实现只接受 60/120/144 Hz，且把 100 Hz 显示器降到 60 Hz。维护者于 2026-10-15 要求确保高刷能力，不等待特定屏幕。旧实现已实际复现拒绝 100 Hz。

公共节拍支持 30–1000 Hz 整数，延续现有显示查询的范围。共享策略校验请求，并直接取请求与显示配置频率的较小值；配置未知时上限为 60 Hz。Windows 的整数配置查询不等于逐帧呈现测量，也不提供分数频率精度。诊断环境覆盖只接受完整范围内十进制字符串，不作为物理高刷证据。

窗口移动和显示设置变更后清空显示配置缓存；保留 SOUI 默认消息处理。计时器失败以实际选择的频率记录，避免请求与显示频率不同而反复重启。继续使用单个待处理通知、跳过迟到帧、有界停止及 Win7 兼容定时器。

Demo 控制接受完整整数范围，先校验 uint64 再收窄，拒绝 32 位整数回绕、非整数和未授权请求。界面增加常见频率并允许按钮换行。测量场景根据实际报告配置选择频率，结束后恢复原请求。

兼容性：既有 60/120/144 请求不变；75/100/165/240 等请求新增可用。低于 60 Hz 的有效配置也被尊重。SDK 的两个纯策略函数分别为 is_supported_frame_rate 和 clamp_frame_rate_to_display；不改变已有类布局。

仅增加 100 Hz 会保留其他高刷档位缺陷；在低刷屏上无条件提高调度率不能证明实际高刷。本次不更改呈现架构或放宽性能门槛。

验证已覆盖双架构两条计时器路径的 13 个频率、边界和诊断字符串、阻塞 UI 合并、切换与停止；真实 Demo 控制覆盖权限、参数、溢出，并保留原交互任务回归。窗口源码双架构实际编译通过。完整候选、实际窗口与当前可用显示条件仍单独记录。
