# SOUI Web SDK 0.3：性能、桌面能力与轻量化

状态：已开始实施；当前先交付 R01/R08/R09 的基础切片，未授权正式发布。编写日期：2026-09-22。
规划源码基线：`9527a4d87014029d3efa1fcd0658f6dff23c3f35`（`0.2.0-preview.2`）；实现进展见 [基础切片记录](0.3-foundation.md)。以下基线数值属于规划时快照。

## 1. 版本目标

本轮直接迭代 SDK：让 Windows 应用获得接近 Electron 的高频桌面能力和流畅性，同时维持小运行包、低空闲消耗、可自行编译的优势。模板用于证明标准接入，Workbench 用于演示和压力场景，不围绕某个业务项目扩展功能。

Demo、独立测试消费者与 Electron 对照如何形成 SDK 生产能力及采用价值的证据，见 [生产能力与价值验证方案](0.3-sdk-validation.md)。其中新增场景、目录与验证档仍为实施提案，不代表已有验收结果。

三项共同验收：

1. **性能可对标**：启动、真实输入响应、滚动/动画、Bridge 往返、后台消耗、重载和退出都有可复现数据。
2. **能力可复用**：常用窗口、应用生命周期、对话框、剪贴板、托盘、菜单、快捷键可由标准 SDK 使用，不必复制 Demo 适配器。
3. **体积受约束**：默认最小应用只带需要的运行依赖；新增桌面功能按模块启用，每个模块报告增量体积与后台成本。

先交付 `0.3.0-preview.N`。功能验收不自动改变 `releaseReady: false`。正式渠道、产品签名、目标系统和二进制再分发仍需各自验收。

## 2. 对齐范围与明确取舍

对齐的是 Windows 上选定的用户行为、API 能力和可测量体验；本轮不承诺 Electron 源代码直接替换运行，不引入完整 Node.js 运行时或 npm 原生扩展兼容层。`node.dll` 在当前交付中是 Miniblink 内核文件，不能据文件名推断具备 Node.js 生态能力。

Electron 的主进程、渲染进程及 utility process 构成不同职责边界；当前 SDK 的线程隔离不能被描述成 Electron 等价的进程隔离。[Electron 进程模型](https://www.electronjs.org/docs/latest/tutorial/process-model)

本轮保留 Chrome 49 页面编译目标，逐项声明浏览器能力。转译与 polyfill 不能补齐完整现代 Chromium。现代网页兼容、独立渲染进程和新内核路线另立研究任务，给出安全、体积、性能、维护成本后再决定；不在主迭代中悄悄换内核。

沿用现有 Windows/x86/x64 构建边界；主要性能对标为 Windows 10/11 x64，x86 保持构建与生命周期回归。具体 Windows 版本、补丁、显卡与驱动在基线阶段登记。Windows 7 能力不因编译宏存在而宣称通过，也不静默取消已有兼容目标。

优先级含义：P0 是稳定性与基础接入门槛；P1 是本轮桌面功能目标；P2 为后续版本或需独立验证的扩展。每项完成都要有最小示例、类型、错误语义、权限和关闭清理测试。

| 能力 | 0.2 状态 | 0.3 目标 | 优先级与约束 |
|---|---|---|---|
| App 生命周期 | 模板手写启动/关闭 | ready、quit、退出拦截、应用路径、版本信息、单实例与第二实例激活 | P0；生命周期先于托盘驻留 |
| 窗口基础 | 有 Host、标题、拖动、最小化/最大化/关闭底层能力 | 统一窗口 ID、显隐、大小/位置、焦点、全屏、置顶、状态事件、DPI 变更 | P0；保持 UI 线程所有权 |

## 5. 性能与体积目标

以下全部是拟定目标，不是当前测量结果。M0 完成后按固定设备和场景冻结门槛；任何调整要记录原因，不能为掩盖回归而提高上限。

### 5.1 测量协议

- 固定 SOUI 基线提交、构建参数、模块清单和实际资源散列；Electron 使用 M0 当时选定的稳定版本并记录精确版本及依赖锁文件。
- 同一设备、系统、显示器刷新率、电源模式、数据、页面组件版本和逻辑。两端均使用发布构建，关闭开发服务器、调试器与额外日志。
- 先测只含公共 Web 特性的相同页面，再测两端实际优化后的同一交互。不同打包器的兼容转换差异要披露，不删减一方负载。
- 场景：空白启动、10,000 条数据的同实现虚拟列表、表单输入/中文 IME、连续 resize、动画、Bridge 并发、目录扫描期间交互、3 窗口切换、最小化/恢复、重载/关闭。
- 热启动至少 30 次、冷启动至少 10 次且记录冷态定义；交互各 5 轮、每轮 60 秒；报告 p50/p95/p99、原始样本及波动区间，不只报平均 FPS。
- 分开记录 DOM/JS 就绪、原生输入排队、显示呈现时刻。通过 OS 输入事件和可用的呈现追踪测量；缺少呈现证据时明确标记，不把 DOM 点击当作物理输入到屏幕延迟。
- 内存/CPU 统计整棵应用进程树。诊断面板和压测工具的开销分别记录；测试结束才写大报告。

Electron 官方也强调测量真实瓶颈、避免阻塞主进程及推迟不必要工作；本轮用本项目数据决定优化顺序。[Electron 性能指南](https://www.electronjs.org/docs/latest/tutorial/performance)

### 5.2 建议验收门槛

| 指标 | 0.3 拟定目标 | 口径 |
|---|---|---|
| 启动到可交互 p95 | 不慢于同负载 Electron；对 0.2 的慢场景争取降低 20% | 冷、热分开；同时观察首帧与首次成功 Bridge 调用 |
| 60 Hz 轻/中负载 | 帧间隔 p95 ≤ 20 ms，超过 33.3 ms 的间隔占比 ≤ 1% | 固定滚动/动画场景；不是所有页面的笼统保证 |
| 输入到呈现 p95 | ≤ 50 ms，且不超过 Electron 对照的 `max(1.15 × p95, p95 + 5 ms)` | 原生输入与呈现证据共同支持 |
| 高刷新率 | 120/144 Hz 单列测试并争取接近每帧预算 | 先作为增益目标；未通过不宣称高刷对齐 |
| 小消息 Bridge 往返 p95 | 1 KiB、单请求 ≤ 5 ms；32 并发场景 ≤ 20 ms | 原生 no-op/echo；真实业务耗时分开报告 |
| 队列与背压 | 队列有硬上限，溢出返回明确结果，压力结束恢复 | 不可用丢关键事件或无界积压换取漂亮数字 |
| 空闲/后台 CPU | 最小静态应用可见均值 ≤ 1%，最小化 ≤ 0.5% | 整机总 CPU 百分比，固定参考机，预热后 5 分钟，无媒体任务 |
| 稳态内存 | 最小应用整进程树 Private Bytes 争取 ≤ Electron 的 70% | 同页、同稳态；该比例是目标，当前尚无测量 |
| 重载稳定性 | 预热后 100 次重载，静置后增长 ≤ `max(16 MiB, 10% 基线)`，并检查增长趋势 | 不通过主动清空工作集伪造回收；8 小时浸泡另行验收 |
| 生命周期 | 至少 1,000 次创建/销毁及退出压力循环，0 崩溃、0 超时；8 小时运行通过 | 区分进程重启与同进程销毁重建；公开支持的模式均测 |
| 默认 Core 体积 | 相对 M0 干净最小包不增加；争取缩小 5%–10% | 解压大小和相同 ZIP 参数大小同时记录 |
| 启用全部 P1 桌面模块 | 相对 Core 增量 ≤ 3 MiB 解压大小 | 不捆绑可选媒体、样例素材、源码与符号 |
| 相对 Electron 体积 | 同场景运行包压缩/解压均争取 ≤ 对照 40% | 两边均含实际必需的运行依赖，不借系统预装资源美化数据 |

默认 Core 体积、生命周期、消息/权限正确性为硬门槛。相对 Electron 的目标首次在 M0 校准；未达到的项目保留差距和数据，不能发布“全面追平”的结论。

### 5.3 优化顺序

1. 生命周期和内存所有权：引擎、WebView、页面 session、异步请求、事件订阅、定时器、窗口资源逐一配对释放。
2. UI/引擎线程去阻塞：异步 Bridge、长任务调度、有界队列，清楚区分页面等待超时与原生取消。
3. 帧调度：按可见性和真实刷新率驱动；合并可替换事件，避免忙轮询、重复无效绘制及落后帧追赶。
4. 启动与资源：按需初始化桌面服务，拆除最小模板的无关资源，清理部署遗留文件，减少无效脚本解析。
5. 只有数据证明内核是主要瓶颈时，再对合成/绘制/内核构建配置做定点优化；保留可回退配置。

## 6. SDK 结构与轻量化设计

沿用现有 `sdk / templates / demos` 分层，在 SDK 内形成模块边界；新增目录/目标名以 ADR 为准，以下不是现有 API。

```text
sdk/
  core        生命周期、Host、会话、权限、异步 Bridge、资源加载
  desktop     app/window/dialog/clipboard/screen/shell
  extensions  tray/menu/shortcut 与后续可选能力
  web         核心客户端 + 按模块导出的类型和连接器
contracts/    核心/桌面契约的单一描述来源（拟新增）
benchmarks/   公共场景 + SOUI/Electron 对照宿主（拟新增）
```

- 默认 Core 不注册高权限桌面方法；模块显式启用，能力发现返回真实可用集合。
- 先采用原生 Win32 适配和可选静态链接模块。CMake 源码目标、链接设置与运行依赖清单同时拆分；仅移动文件夹不算完成模块化。
- 原生静态库未使用代码是否消除，由链接 map 与最终包测量验证；Web 端按需导出也必须检查实际经典脚本。
- Core 运行包、桌面扩展、SDK 开发包、完整依赖源码、Demo 和符号包分开交付。完整源码可大，最终应用必须小。
- 默认应用保持 Chrome 49 经典脚本入口。Demo 的现代/legacy 双产物不自动全部复制到最小应用。
- 移除 CRT 或系统 DLL 前证明目标机依赖闭包完整；不靠少带必需运行库制造体积优势，不默认使用 UPX。
- 优先原生轻量封装；FFmpeg、现代浏览器内核等大型依赖不进入默认 Core。

必须先形成的 ADR：进程级 Runtime 与多窗口所有权、异步 Bridge/契约与兼容、模块化及包格式、性能测量协议。设计应包括状态/线程、失败恢复、迁移与体积影响。

| R02 | 性能/体积基线 | 固定场景、两种宿主、输入/呈现、内存/CPU、包清单 | R01 | 同机对照报告与原始数据；冻结设备/门槛 |
| R03 | Runtime 生命周期 | engine/host/session/任务/事件关闭，多窗口先导实验 | R02 | 重载、并发关闭、进行中任务取消、8 小时日志；无新增进程泄漏 |

R03 的多窗口实验是早期风险点：必须先证明多个 WebView 能共享进程级内核且最后一个窗口关闭才释放内核。若做不到，在 M1 报告并调整多窗口里程碑；不能在后期用反复全局初始化或强制结束进程掩盖问题。

R01/R09 中的版本规则必须统一：同一版本只对应一个 SDK 载荷；开发提交可未发布，但不得覆盖已产生的同版本发布包。本轮 `preview.N` 严格递增。新增清单格式须支持从现有 v1 包迁移，正式渠道支持留到专门版本契约变更。

## 8. 里程碑与工期假设

估算假设：1 名 C++/运行时工程师 + 1 名 Web/工具链工程师，维护者承担评审，另有约 0.5 人力用于测试；设备与开发工具已准备。8–10 周开发验收窗口，另预留 2 周处理内核问题；单人串行约 14–18 周。此为规划估算，M0 后重估，不承诺具体日期。

| 里程碑 | 建议时段 | 内容 | 退出门槛 |
|---|---|---|---|
| M0 基线 | 第 1 周 | R01、R02 起步；模块与测量 ADR；多窗口可行性先导 | 干净克隆校验和构建通过，固定性能/体积基线，风险有负责人 |
| M1 性能底座 | 第 2–3 周 | R03、R04；R05 定位；R08 开始 | 关键关闭/重载问题可复现并有修复证据；异步事件路径完成；多窗口 go/no-go |
| M2 性能预览 | 第 4–5 周 | R05、R06 核心；R08 Core 体积控制 | 后续 preview 候选：核心性能数据、标准服务、最小包预算 |
| M3 桌面能力预览 | 第 6–7 周 | R06 完整、R07、R09 | 后续 preview 候选：完整 P1 能力矩阵、3 窗口与驻留交互回归 |
| M4 收敛 | 第 8–10 周 | R08/R09/R10、矩阵/长时验证 | 后续 preview 候选：全量证据、差距表、迁移文档、可回退交付 |

关键路径：可信基线 → 生命周期 → 异步协议 → 多窗口/桌面模块 → 完整包与回归。功能开发可与测量/模块工具并行，但验收阶段串行占用同一桌面测试机，避免负载干扰。

固定时间不够时，先移出 P2，再缩减 P1 的高级选项；P0 的生命周期、权限、体积和证据完整性不降级。多窗口的 go/no-go 结果必须显式调整计划，不能把缺失能力标为完成。

## 9. AI 开发与本机验收

不恢复远程 CI。保留现有 [AGENTS.md](../../AGENTS.md) 中的分支、PR、评审和本机验证规则。

每个工作包实施前建立问题与验收条目，写清源码范围、受影响对象、线程/状态变化、基线数据、回退点和失败路径。每个 PR 只交付可独立核验的改动，不把生命周期重构、依赖升级和 UI 美化混在一起。

PR 至少记录：提交/源码身份、实际命令、架构/配置、结果路径、适用性能差异、Core/模块体积差异、未执行项。公开 API、协议、线程、运行依赖和发布流程按 AGENTS 由维护者评审。

计划扩展现有 `tools/Test.ps1` 与验收收集器，提供本机分档验证。下表是拟新增验证档，不是当前可运行参数：

| 验证档 | 使用时机 | 内容 |
|---|---|---|
| 快速 | 相关代码变更 | 单元/契约、类型/生成检查、SDK 安装器行为 |
| 原生集成 | Host、Bridge、窗口变更 | 真实启动/页面调用/事件、取消、重载、关闭、模块权限 |
| 性能 | 渲染、线程、序列化、资源变化 | 固定场景，与 M0 和上一个接受版本对照 |
| 体积 | 每次模块/资源/依赖变化 | 干净暂存、逐文件与各模块字节统计、依赖闭包 |
| 发布 | 每个候选 | x86/x64 × Debug/Release、目标 Windows、DPI/IME、多窗口、8 小时、源码搬移、升级/回退 |

证据需绑定 source/package/build identity、完整运行载荷（含 HTML/JS/CSS/DLL）、架构、配置、工具链、场景版本、完成时间与原始结果。修改任意被测载荷后旧成功记录不能继续授权打包。诊断日志默认本地保存并限制大小，禁止记录 token 和用户文件内容。

本轮必须交付：SDK 源码与开发包、最小 Core 应用、可选桌面模块、精简示例、完整 Workbench、可复跑 benchmark、性能与大小报告、0.2→0.3 迁移指南、能力差异表、符号/诊断说明与本机发布检查表。

## 10. 后续路线

## 11. 规划核验说明

本轮只读取源码、历史验收与本机文件大小，并比较 Git 文件集合和源码清单；未重跑性能测试、底层重编译或发布验收，没有产生新的性能达标结论。Electron 能力参考官方文档，访问日期 2026-09-22，实际 benchmark 的具体 Electron 版本由 M0 锁定。

父项目的认知导航报告图数据库缺失，本规划用上面列出的具体源码与文档进行有界核对；未将历史图信息当作事实，也未自动进入 Spec Kit 特性或地图重建工作流。

本文件中的指标和完整能力仍是迭代目标；实际结果按工作包记录。基础切片已使用 preview.1/preview.2 的开发身份，尚未形成 M2 候选发布；后续候选从未占用的序号继续递增，不能覆盖相同版本或根据序号推断某个里程碑已完成。未实现的目录、命令或目标不能描述为已支持。
