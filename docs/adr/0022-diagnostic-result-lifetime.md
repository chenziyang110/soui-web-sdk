# ADR-0022：有期限的引擎诊断结果所有权

- 日期：2026-10-08
- 状态：实施；原生验证由本轮集成构建记录绑定，真实桌面与长稳未执行
- 范围：Miniblink 的内存回收诊断；不修改公共 API、引擎 FIFO 或生命周期关闭顺序

## 背景

`engine_thread::invoke()` 等待超过期限时返回 false，但已经接纳的任务仍可能排队或正在执行。它不是取消 API。`SOUI_PERFORMANCE_DIAGNOSTICS` 下的 `request_memory_recovery()` 将栈上 `host_result` 以引用交给该任务；默认十秒期限耗尽后，调用返回、结果销毁，迟到的任务仍可写入已结束的栈对象。

这是源码确认的生命周期缺陷。本轮没有运行真实 Miniblink；它不证明历史 x86 挂载超时、GPU USER 对象增长或内存趋势的原因。

## 决定

诊断结果采用共享所有权，工作闭包捕获拥有该结果的对象。只有 `invoke()` 明确确认工作完成才读取结果；超时、拒绝或工作抛异常返回已有失败语义，不读取可能仍在写入的结果。迟到任务完成或被关闭队列丢弃后自行释放结果与工作闭包。

把此规则放在私有的有期限诊断调用 helper 中，实际内存回收调用与无窗口回归测试使用同一实现。该 helper 不安装为公共头文件，也不拥有 Host、WebView 或 Runtime；诊断闭包不捕获 adapter。`engine_thread::invoke()` 的期限、异常处理与不能取消正在执行任务的契约不变。真正的 `mount`/`unmount` 仍使用现有生命周期屏障，不能用诊断超时绕过关闭安全。

## 备选方案

- 超时后仍等待任务结束：违背诊断有期限返回的目的。
- 从 FIFO 删除尚未执行任务：不能覆盖已执行任务，且扩大会话与引擎调度的修改范围。
- 捕获栈引用但把超时改大：仍存在同一生命周期缺陷。
- 只在测试中复制共享结果示例：没有保护真实调用路径，采用实际调用共用的私有 helper。

## 兼容、迁移与回退

保持 `host_result` 形状、`E_ENGINE_THREAD` / `E_GC_API_MISSING` 以及现有成功消息。只影响显式诊断构建，不改变正常版的回收策略、最低 Windows 版本或固定内核输入。新的 SDK 内容须随 0.5 新身份交付，不能覆盖已有 0.4 固定包。回退此改动会恢复已知栈引用风险。

## 验证

无窗口测试在实际 `engine_thread` FIFO 上先接纳阻塞任务，并以 promise 确认其已经进入，再提交短期限诊断。先观察诊断返回超时、迟到工作尚未进入；随后释放阻塞任务，验证工作确实执行、调用方失败结果不变、工作闭包最终释放。另覆盖正在执行时超时、正常完成、拒绝与抛异常。所有交错使用 promise/future 同步；短期限仅触发被测 API 的真实超时，不用 Sleep 猜执行顺序。

测试运行结果、两架构构建与必要的 sanitizer 检查只在实际执行后记录。该无窗口回归不关闭真实 GC API、GPU、资源趋势、历史超时或八小时稳定性门槛。
